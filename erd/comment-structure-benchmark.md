# 댓글 구조 성능 비교: 지금 방식 vs 클로저 테이블

- 날짜: 2026-10-07
- 환경: PostgreSQL 16, 클라우드 컨테이너 1대, pgbench 동시 접속 4, 시나리오마다 15초
- 스크립트: [bench/](bench/) (`setup.sql`이 데이터를 만들고, 나머지 6개가 시나리오)
- 결론: **지금 방식(답글 1단계 + DB가 깊이 강제)을 유지한다.** 읽기 약 3배, 쓰기 약 1.7배 빠르고 저장 공간은 절반이다.

## 비교한 두 방식

| | A. 지금 방식 (V3) | B. 클로저 테이블 |
|---|---|---|
| 구조 | `comment.parent_id` + 생성 컬럼과 복합 FK로 "부모는 최상위만" 강제 | `comment`에는 계층 정보 없음, `comment_tree(ancestor_id, descendant_id, depth)`에 자기 자신(0)과 부모(1) 행 |
| 깊이 | 1단계 고정 (spec 011 FR-010) | 몇 단계든 가능 |
| 재귀 쿼리 | 필요 없음 | 필요 없음 |

## 데이터

- 댓글 1,021,950개: 글 20,000개, 글마다 최상위 10개와 각각 답글 4개
- 인기 글 1개: 최상위 2,000개, 각각 답글 10개
- 클로저 테이블 행 1,841,910개

## 결과

| 시나리오 | A. 지금 방식 | B. 클로저 테이블 | 차이 |
|---|---|---|---|
| 글 상세 첫 화면 (최상위 20개 + 답글 3개씩 + 답글 수), 아무 글 | **0.23 ms** (17,279건/초) | 0.71 ms (5,605건/초) | A가 3.1배 빠름 |
| 같은 화면, 댓글 2만 개인 인기 글 | **0.36 ms** (11,090건/초) | 1.29 ms (3,101건/초) | A가 3.6배 빠름 |
| 답글 쓰기 | **0.69 ms** (5,763건/초) | 1.18 ms (3,394건/초) | A가 1.7배 빠름 |
| 저장 공간 (표 + 인덱스) | **242 MB** | 431 MB | A가 44% 작음 |

## 왜 이런 차이가 나나

- A는 인덱스 두 개(`ix_comment_root`, `ix_comment_reply`)를 정렬 순서 그대로 읽고 멈춘다(LIMIT).
- B는 최상위를 고르려면 "부모가 없는 댓글"을 찾는 NOT EXISTS 조인이 필요하다. 답글을 작성 순서로 3개 고를 때도 `comment_tree`와 `comment`를 조인한 뒤 정렬한다.
- B는 답글 하나를 쓸 때 댓글 1행과 계층 2행을 써야 한다.

## 언제 B로 바꾸나

여러 단계 답글(답글의 답글을 들여 쓰기)로 기획이 바뀌면 B가 맞다. 그때 A는 `WITH RECURSIVE`가 필요해지고, B는 깊이와 상관없이 조인 한 번으로 하위 전체를 읽는다. 지금 spec(1단계)에서는 B의 장점을 쓸 일이 없고 비용만 든다.
