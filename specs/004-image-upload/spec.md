## User Scenarios & Testing *(mandatory)*

### User Story 1 - 본문에 사진 넣기 (Priority: P1)

작성자가 사진을 붙여넣거나 끌어놓으면 브라우저가 사진을 줄이고 촬영 위치 같은 메타데이터를 지운 뒤 목록용 썸네일과 함께 저장소에 바로 올린다. 서버가 실제 파일을 다시 검사해 통과하면 본문에는 사진 주소만 들어간다.

**Why this priority**: C-IMG-1의 핵심. 이것만 있어도 사진이 있는 글을 쓸 수 있다.

**Independent Test**: 테스트 회원이 5MB 휴대폰 사진(GPS 포함)을 본문에 넣고, 본문에 주소가 들어갔는지, 저장된 파일이 줄어들고 위치 정보가 없는지, 썸네일이 함께 생겼는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이메일 인증 회원의 편집 화면, **When** jpg·png·webp 사진을 넣으면, **Then** 긴 변 최대 1920px로 줄고 WebP로 변환되며 위치 정보가 제거된 원본과 가로 최대 640px 썸네일이 올라가고, 본문에는 사진 주소만 들어간다.
2. **Given** 업로드를 시작한 사진, **When** 서버가 두 파일을 확인하면, **Then** 실제 존재·실제 크기·실제 파일 형식·해상도를 검사해 통과한 경우에만 주소를 돌려주고, 실패하면 올라간 파일을 지운다.
3. **Given** 확장자만 jpg로 바꾼 다른 형식의 파일, 손상된 파일, 1만 px를 넘는 초대형 해상도, 10MB 초과 파일, **When** 올리면, **Then** 거부되고 이유가 표시된다.
4. **Given** 올라간 사진, **When** 저장 위치를 보면, **Then** 파일 이름은 서버가 만든 추측할 수 없는 이름이고, 사용자가 올린 원래 파일 이름은 어디에도 저장·표시되지 않는다.
5. **Given** 1분에 20장을 넘게 올리려는 회원, **When** 21번째를 올리면, **Then** 거부되고 잠시 뒤 다시 시도하라는 안내가 나온다.
6. **Given** 비회원 또는 이메일 인증 전 회원, **When** 사진 업로드를 시도하면, **Then** 각각 로그인·이메일 인증이 필요하다는 이유로 거부된다.

---

### User Story 2 - 오프라인·실패한 업로드도 잃지 않기 (Priority: P2)

연결이 끊기거나 업로드가 실패해도 사진은 이 기기에 대기하고 본문에는 정상적으로 보인다. 연결이 돌아오면 자동으로 다시 올라가 진짜 주소로 바뀐다. 대기 사진이 남은 글은 발행되지 않는다.

**Why this priority**: 자동 저장(003)이 오프라인을 지원하므로 사진도 같이 지원해야 글이 깨지지 않는다.

**Independent Test**: 오프라인에서 사진을 넣고 화면에 보이는지, 발행이 거부되는지, 온라인으로 돌린 뒤 자동으로 업로드되어 주소가 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 오프라인, **When** 사진을 넣으면, **Then** 사진이 이 기기 대기열에 저장되고 본문에는 "업로드 대기" 임시 표시가 들어가며 화면에는 사진이 정상으로 보인다.
2. **Given** 대기 사진이 있는 글, **When** 자동 저장이 일어나면, **Then** 임시 표시가 있는 그대로 저장된다.
3. **Given** 대기 사진이 있는 글, **When** 발행하면, **Then** 업로드가 끝나지 않은 사진이 있다는 이유로 발행이 거부된다.
4. **Given** 연결이 돌아옴, **When** 재시도가 성공하면, **Then** 본문의 임시 표시가 진짜 사진 주소로 바뀐다.
5. **Given** 대기 중인 사진, **When** 작성자가 취소하면, **Then** 대기열과 본문의 임시 표시가 함께 사라진다.

---

### User Story 3 - 사용량과 한도 (Priority: P3)

한 사람이 저장소를 다 채우지 못하도록 회원마다 1GB, 하루 200장의 한도가 있고, 작성자는 설정 화면에서 사용량을 본다.

**Why this priority**: 공유 저장소를 지키는 운영 안전장치다. 업로드가 동작한 뒤에 의미가 있다.

**Independent Test**: 사용량을 한도 직전까지 채운 회원으로 여러 장을 동시에 올려 한도를 넘지 않는지, 201번째 장이 거부되는지, 설정 화면 표시가 맞는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 지금 사용량 + 이번 사진(원본 + 썸네일)이 1GB를 넘는 회원, **When** 업로드를 시작하면, **Then** "사진 저장 공간(1GB)을 다 썼어요…" 안내와 함께 거부된다.
2. **Given** 한도 직전의 회원, **When** 여러 장을 동시에 올리면, **Then** 합계가 한도를 넘는 장은 거부되어 총합은 한도를 넘지 않는다.
3. **Given** 오늘(한국 시간 0시 기준) 200장을 시작한 회원, **When** 201번째를 시작하면, **Then** "오늘은 사진을 200장까지 올릴 수 있어요" 안내와 함께 거부된다. 실패한 업로드도 한 장으로 센다.
4. **Given** 회원의 설정 화면, **When** 열면, **Then** "사용량 / 1GB" 막대와 "지운 사진의 공간은 7일 뒤 돌아와요"가 보인다. 90%를 넘으면 편집기의 사진 버튼 옆에 남은 공간이 안내된다.

---

### User Story 4 - 대체글과 움직이는 GIF (Priority: P4)

작성자는 사진마다 대체글을 넣도록 권유받지만 강제되지는 않는다. GIF는 움직임이 그대로 살아 있되 본문에서는 처음에 멈춘 장면으로 보이고, 누르면 재생된다.

**Why this priority**: 접근성과 데이터 절약. 기본 업로드 위에 얹는 표시 규칙이다.

**Independent Test**: 대체글 없는 사진 2장이 있는 글을 발행해 안내가 나오고 발행은 되는지, GIF가 정지 장면 + ▶로 보이다 누르면 움직이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 대체글이 빈 사진 2장이 있는 글, **When** 발행 설정 창을 열면, **Then** "대체글이 없는 사진이 2장 있어요 [대체글 넣기]" 안내와 사진별 입력칸이 나오고, 입력하지 않아도 발행된다.
2. **Given** 대체글이 빈 사진, **When** 독자 화면에 그려지면, **Then** 화면 낭독기가 건너뛰는 빈 대체글로 그려지고 파일 이름·주소가 읽히지 않는다.
3. **Given** GIF, **When** 올리면, **Then** 원본은 변환 없이 그대로 올라가고 썸네일은 첫 장면이다.
4. **Given** 가로 또는 세로 1920px 초과, 또는 300프레임 초과 GIF, **When** 올리면, **Then** 고르는 순간 또는 서버 검사에서 거부되고 올라간 파일은 지워진다.
5. **Given** 본문의 GIF, **When** 독자가 보면, **Then** 처음에는 정지 장면 + ▶ 표시, 누르면(키보드 Enter 포함) 재생, 다시 누르면 정지된다. 스크립트가 동작하지 않으면 원본 GIF가 새 탭에서 열린다.
6. **Given** 움직이는 WebP·PNG, **When** 올리면, **Then** 첫 장면만 남으며 업로드 화면에 이 사실이 안내된다.

### User Story 5 - 버려진 사진 정리와 프로필 사진 보호 (Priority: P5)

글에서 빠진 사진과 올리기만 하고 쓰지 않은 사진은 일정 기간 뒤 자동으로 지워져 공간이 돌아온다. 지금 쓰는 프로필 사진은 지워지지 않는다.

**Why this priority**: 저장소 비용과 용량 회수. 업로드·발행이 동작한 뒤에 필요하다.

**Independent Test**: 올리기만 한 사진(24시간 경과), 글에서 뺀 사진(7일 경과), 현재 프로필 사진, 바꾼 이전 프로필 사진(7일 경과)을 준비해 정리 작업 후 앞의 둘과 이전 프로필만 지워지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 올렸지만 어떤 글·프로필에도 연결되지 않은 채 24시간이 지난 사진, **When** 매일 정리 작업이 돌면, **Then** 원본·썸네일 파일과 기록이 지워지고 용량이 돌아온다.
2. **Given** 글에 연결됐다가 저장·발행으로 본문에서 빠진 지 7일이 지난 사진, **When** 정리 작업이 돌면, **Then** 지워진다. 7일이 안 됐으면 남는다.
3. **Given** 지금 연결된 프로필 사진, **When** 정리 작업이 돌면, **Then** 지워지지 않는다. 회원당 현재 프로필 사진은 하나뿐이다.
4. **Given** 프로필 사진을 바꾸거나 기본 이미지로 돌린 경우, **When** 7일이 지나면, **Then** 이전 프로필 사진이 정리된다.
5. **Given** 탈퇴 후 30일 익명 처리가 끝난 회원, **When** 그다음 정리 작업이 돌면, **Then** 그 회원이 올린 사진이 모두 지워지고 프로필 사진 연결도 비어 있다.
6. **Given** 저장소 파일 삭제가 실패함, **When** 다음 정리 작업이 돌면, **Then** 다시 시도되고 파일이 지워진 뒤에만 기록이 지워진다.

### User Story 6 - 사진 주인과 접근 범위 지키기 (Priority: P6)

사진은 올린 사람의 것이다. 남이 올린 사진 주소를 내 글에 붙여도 내 글에 연결되지 않고 링크로만 보인다. 저장소의 사진은 주소를 아는 사람만 하나씩 볼 수 있고 목록은 열리지 않는다.

**Why this priority**: 남의 사진을 지우게 하거나 용량을 떠넘기거나 비공개 글 사진을 노출하는 악용을 막는다.

**Independent Test**: 회원 두 명으로 B가 A의 사진 주소를 글에 넣어 발행한 뒤 링크로만 보이고 A의 글에서는 그대로 보이는지, 저장소 목록 조회가 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 남이 올린 사진 주소가 든 내 글, **When** 발행하면, **Then** 그 사진은 내 글에 연결되지 않고 링크로 그려지며, 원래 주인의 글에서는 그대로 보인다.
2. **Given** 남이 올린 사진, **When** 그 사진의 업로드 완료 확인을 내가 요청하면, **Then** "찾을 수 없음"으로 응답한다.
3. **Given** 저장소, **When** 로그인하지 않은 사람이 사진 목록을 조회하거나 허용 경로 밖 파일을 읽거나 허가 없이 파일을 쓰면, **Then** 모두 거부된다. 사진 주소 하나로는 그 파일을 읽을 수 있다.
4. **Given** 업로드 허가, **When** 위조·경로 변경·형식 불일치·5분 만료 상태로 쓰면, **Then** 거부된다. 우리 사이트가 아닌 출처의 브라우저 업로드도 거부된다.
5. **Given** 사진 공개 주소를 새 주소로 바꾸고 기존 글을 다시 렌더링함, **When** 독자가 옛 주소로 쓰인 우리 사진을 보면, **Then** 링크가 아니라 사진으로 보인다. 목록에 없는 주소의 사진은 외부 이미지 링크가 된다.

---

### Edge Cases

- 서버가 확인한 실제 크기가 업로드 시작 때 신고한 크기보다 큼 → 거부하고 파일을 지운다.
- 썸네일이 가로 640px 또는 1MB를 넘음 → 거부한다.
- 프로필 사진 → 정확히 256×256, 1MB 이하만 받고 썸네일은 만들지 않는다 (프로필 화면 자체는 프로필 spec).
- 글을 지움 → 사진 공간은 바로 돌아오지 않고 정리 작업이 실제로 파일을 지울 때 돌아온다.
- 비공개 글의 사진 → 주소를 알면 볼 수 있다 (팀 결정). 주소는 추측할 수 없고 목록은 닫혀 있다.
- 독자 브라우저에 이미 캐시된 지운 사진 → 최대 1년 남을 수 있는 허용 한계로 둔다.
- 다른 환경(개발용) 사진 주소를 운영 글에 붙임 → 우리 사진으로 보지 않고 외부 이미지 링크가 된다.
- GIF의 기타 메타데이터 → 서버가 파일을 고치지 않으므로 남을 수 있는 알려진 한계다.
- 운영 저장소에서 브라우저 직접 업로드 허용 설정을 할 수 없음 → [NEEDS CLARIFICATION: 운영 저장소(NHN)에서 우리 사이트 출처의 직접 업로드 허용 설정이 가능한가? 불가하면 앱 서버 경유 업로드로 바꾼다고 문서에 정해져 있으나, 배포 전 확인 결과에 따라 업로드 경로와 서버 부하 목표가 달라진다 (52 §11.2 배포 세부 구성)]

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 이메일 인증을 마친 회원만 사진을 올릴 수 있어야 한다. 비회원은 로그인 필요, 인증 전 회원은 인증 필요로 거부한다.
- **FR-002**: 시스템은 jpg·png·gif·webp, 원본 10MB 이하만 받아야 한다.
- **FR-003**: 브라우저는 업로드 전에 GIF가 아닌 사진을 긴 변 최대 1920px·WebP(품질 0.8)로 바꾸고 촬영 위치 등 메타데이터를 제거해야 한다. GIF 원본은 변환하지 않는다.
- **FR-004**: 브라우저는 가로 최대 640px WebP 썸네일(GIF는 첫 장면)을 함께 만들어 올려야 한다.
- **FR-005**: 사진 데이터는 앱 서버를 거치지 않고, 서버가 사진마다 발급한 5분 유효 업로드 허가로 저장소에 직접 올라가야 한다.
- **FR-006**: 업로드 허가를 발급할 때 서버는 형식·크기·요청 횟수(1분 20장)·용량 한도·하루 한도를 검사해야 한다.
- **FR-007**: 업로드 완료를 확인할 때 서버는 원본·썸네일의 존재, 실제 크기, 파일 앞부분으로 판정한 실제 형식, 해상도(1만 px 초과 거부, 썸네일 가로 640px·1MB 이하, GIF 1920px·300프레임 이하)를 검사하고, 실패하면 파일을 지워야 한다.
- **FR-008**: 저장 파일 이름은 서버가 연·월과 추측할 수 없는 식별자로 만들어야 하며, 사용자가 올린 원래 파일 이름은 저장하거나 보여 주지 않아야 한다.
- **FR-009**: 본문에는 사진 주소만 들어가야 한다. 사진 데이터는 자동 저장 경로에 들어가지 않는다.
- **FR-010**: 업로드가 실패하거나 오프라인이면 사진을 기기 대기열에 저장하고 본문에 임시 표시를 넣고, 연결되면 자동 재시도해 성공 시 진짜 주소로 바꿔야 한다. 대기 사진은 취소할 수 있고, 로그아웃 시 그 회원의 대기열은 지워진다.
- **FR-011**: 업로드 대기 표시가 남은 글은 발행이 거부되어야 한다 (자동 저장은 허용).
- **FR-012**: 회원당 사용량(그 회원이 올린 모든 사진의 원본 + 썸네일, 정리 대기 포함, 프로필 포함)은 1GB를 넘을 수 없어야 하며, 동시에 여러 장을 요청해도 넘지 않아야 한다 (설정값).
- **FR-013**: 회원당 하루(한국 시간 0시 기준) 업로드 시작은 200장까지여야 하며 실패한 업로드도 센다 (설정값).
- **FR-014**: 회원은 본인의 사용량·한도·오늘 올린 장수를 볼 수 있어야 하고, 한도 초과·하루 한도·90% 초과 때 편집기에서 안내받아야 한다.
- **FR-015**: 편집기는 사진을 넣을 때 대체글을 비워 두고, 발행 설정 창에서 대체글이 빈 사진의 수를 알려 입력을 권유해야 한다. 대체글이 없어도 발행은 막지 않으며 빈 대체글은 낭독기가 건너뛰는 형태로 그린다.
- **FR-016**: 본문의 우리 GIF는 처음에 첫 장면 + ▶ 표시로 보여 주고, 누르거나 Enter를 누르면 재생, 다시 누르면 정지해야 한다. 스크립트가 없으면 원본을 새 탭으로 연다. 글 카드 썸네일은 첫 장면, 링크 미리보기는 원본을 쓴다.
- **FR-017**: 저장·DB 반영·발행 때 본문의 우리 사진 중 글 작성자가 올린 사진만 글에 연결하고, 연결된 사진은 "사용 중", 빠진 사진은 빠진 시각을 기록해야 한다. 첫 사진의 썸네일이 글 썸네일이 된다.
- **FR-018**: 남이 올린 사진은 내 글에 연결하지 않고 외부 이미지처럼 링크로 그리며, 남의 사진에 대한 업로드 완료 확인은 "찾을 수 없음"으로 응답해야 한다.
- **FR-019**: "우리 사진" 판별은 현재 공개 주소 또는 옛 공개 주소 목록으로 시작하고 나머지가 저장 이름 규칙에 맞는지로 해야 하며, 렌더링할 때 현재 공개 주소로 바꿔 그린다. 작성자의 원문 본문은 고치지 않는다.
- **FR-020**: 매일 한 번, 연결 없이 24시간 지난 사진과 연결이 끊긴 지 7일 지난 사진의 원본·썸네일 파일을 지운 뒤 기록을 지워야 한다. 파일 삭제는 영구 저장 확정 밖에서 하고, 실패하면 다음 회차에 다시 시도한다.
- **FR-021**: 현재 연결된 프로필 사진은 정리 작업이 지우지 않아야 하며, 회원당 현재 프로필 사진은 하나여야 한다. 바꾸거나 기본으로 돌린 이전 프로필 사진은 7일 규칙을 따른다.
- **FR-022**: 탈퇴 30일 익명 처리 시 그 회원의 프로필 사진 연결을 비우고 올린 사진 전부를 정리 대상으로 만들어, 그다음 정리 작업에서 지워야 한다.
- **FR-023**: 사진 파일은 주소가 바뀌지 않으므로 1년간 변경 없음으로 캐시되게 해야 한다.
- **FR-024**: 저장소는 로그인 없는 사람에게 허용 경로 안의 파일 하나 읽기만 허용하고, 목록 조회·허가 없는 쓰기·허용 경로 밖 읽기는 거부해야 한다. 앱은 쓰기·읽기·삭제 권한만 가진 전용 자격 증명을 쓴다. 관리 화면은 외부에 열지 않는다.
- **FR-025**: 업로드 허가는 위조·경로 변경·형식 불일치·만료 시 거부되어야 하며, 브라우저 직접 업로드는 우리 사이트 출처에서만 허용해야 한다.
- **FR-026**: 비공개 글의 사진도 주소를 아는 사람은 볼 수 있다 (팀 결정, 친구 공개 도입 시 재검토).

### Key Entities

- **사진(image)**: 올린 회원, 용도(글/프로필), 상태(임시/사용 중), 형식, 원본·썸네일 크기, 가로·세로, 저장 이름(원본·썸네일), 연결이 끊긴 시각, 만든 시각.
- **글-사진 연결(post_image)**: 글과 그 글 작성자가 올린 사진의 다대다 연결. 정리 작업과 글 썸네일의 근거.
- **업로드 대기 사진**: 기기에만 있는 사진 데이터와 본문 임시 표시 식별자.
- **사용량**: 회원별 사진 크기 합계(별도 저장하지 않고 사진 기록에서 계산)와 하루 업로드 장수.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 일반 휴대폰 사진(약 5MB)은 업로드 전 원래 전송량의 약 10분의 1(300~500KB) 수준으로 줄고, 저장된 파일에서 위치 정보가 검출되는 경우는 0건이다.
- **SC-002**: 확장자 위장·손상·초대형 해상도·한도 초과 GIF 시험 파일은 100% 거부되고 저장소에 남지 않는다.
- **SC-003**: 사용량 한도 직전에서 동시 업로드 10건을 보내도 사용량이 1GB를 넘는 경우는 0건이고, 하루 201번째 업로드 시작은 100% 거부된다.
- **SC-004**: 대체글이 없는 사진이 있는 글은 100% 발행되고, 원래 파일 이름은 어떤 화면·주소에도 나오지 않는다.
- **SC-005**: GIF는 움직임이 유지되며, 본문 첫 표시는 정지 장면 + ▶, 누르면 재생, 스크립트가 없으면 원본 링크로 열린다 (브라우저 종단 시험).
- **SC-006**: 정리 작업 후 기한이 지난 미사용 사진은 0장 남고, 현재 연결된 프로필 사진과 글에 연결된 사진은 하나도 지워지지 않는다.
- **SC-007**: 탈퇴 익명 처리 후 첫 정리 작업이 끝나면 그 회원이 올린 사진은 저장소에 0장이다.
- **SC-008**: 저장소 접근 시험 11가지(정상 업로드 허용, 위조·경로 변경·형식 불일치·만료·허가 없는 쓰기 거부, 목록 조회 거부, 파일 하나 읽기 허용, 경로 밖 읽기 거부, 우리 출처 허용·다른 출처 거부)를 개발 환경과 운영 환경 모두에서 통과한다 (운영은 배포 전).
- **SC-009**: 공개 주소를 바꾸고 다시 렌더링한 뒤에도 옛 주소로 쓰인 우리 사진은 100% 사진으로 보이고, 목록에 없는 주소는 100% 링크로 보인다.
- **SC-010**: 회원 두 명 시험에서 남이 올린 사진을 넣어 발행해도 그 사진은 내 글에 연결되지 않고, 원래 주인의 글에서 계속 보인다.

## Assumptions

- 저장소 제품·운영 방식은 팀 결정(2026-10-06 결정, 2026-10-07 확인)을 따르며 상세 설정과 검증 방법은 근거 문서에 있다. spec은 동작만 정한다.
- 자동 저장(003-draft-autosave)과 발행(005-post-publish)은 별도 spec이다. 발행 거부 규칙(FR-011)과 사진 연결(FR-017)은 발행 spec과 함께 시험한다.
- 프로필 편집 화면·프로필 사진 연결 흐름(C-AUTH-2)과 탈퇴 처리 순서([13](../../docs/13-delete-withdraw.md)·[44](../../docs/44-withdraw.md))는 별도 spec이며, 여기서는 정리 규칙과 보호만 다룬다.
- 글 카드에서 썸네일을 어떻게 배치·자를지는 각자 자유이고, 640px 썸네일 생성만 공통 규칙이다.
- CDN 도입·무효화, 외부 배지 이미지 허용 등은 개인 확장으로 범위 밖이다.
- 수치(크기·해상도·한도·기한)는 설정값이며 위 값은 초기값이다.
