## User Scenarios & Testing *(mandatory)*

### User Story 1 - 글을 지우면 즉시 어디에서도 보이지 않는다 (Priority: P1)

작성자가 자기 글(임시글이든 발행 글이든)을 삭제하면, 확인 후 글이 휴지통으로 옮겨지고 그 즉시 상세·모든 목록·검색·sitemap·글 수에서 사라진다. 작성자 본인에게도 상세는 "찾을 수 없음"이고 휴지통에서만 보인다.

**Why this priority**: 삭제의 기본 약속("지운 글은 바로 사라진다")이다. 이것만으로도 사용자는 원치 않는 글을 내릴 수 있다.

**Independent Test**: 댓글·좋아요가 달린 공개 글을 삭제한 뒤 상세·홈·블로그·태그·검색·sitemap·글 수·휴지통을 확인하면 단독으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 작성자의 공개 발행 글, **When** [삭제]를 누르면, **Then** "휴지통으로 옮길까요? 30일 뒤 완전히 삭제돼요" 확인창이 뜨고, [휴지통으로]를 고르면 글이 휴지통으로 간다.
2. **Given** 휴지통으로 옮긴 글, **When** 누구든(작성자 포함) 상세 주소를 열면, **Then** "찾을 수 없음"이고 없는 글과 같은 응답이다.
3. **Given** 휴지통으로 옮긴 글, **When** 홈·블로그·태그·검색·sitemap을 보면, **Then** 그 글은 나오지 않고 블로그 글 수·태그 글 수에서도 빠지며, 그 글의 댓글·좋아요도 보이지 않는다.
4. **Given** 휴지통에 있는 글, **When** 작성자가 그 글을 저장·자동 저장·발행·공개 범위 변경하려 하면, **Then** "찾을 수 없음"으로 거절된다.
5. **Given** 이미 휴지통에 있는 글, **When** 다시 삭제를 요청하면, **Then** 상태는 그대로이고 성공으로 응답한다.
6. **Given** 작성 중 자동 저장된 내용이 있는 글, **When** 휴지통으로 옮기면, **Then** 마지막 자동 저장 내용까지 보존되어 복구 시 함께 돌아온다.

---

### User Story 2 - 실수로 지운 글을 원래대로 되살린다 (Priority: P1)

작성자는 내 글 관리의 휴지통에서 지운 글을 30일 안에 복구한다. 복구한 글은 원래 상태·공개 범위·목록 위치·댓글·좋아요·태그가 삭제 전과 같다.

**Why this priority**: 휴지통 방식을 고른 이유(실수로 지운 글 되살리기)다. 복구가 원래 모습과 다르면 휴지통이 의미가 없다.

**Independent Test**: 공개 글과 비공개 글, 임시글을 각각 삭제·복구한 뒤 삭제 전과 상태·공개 범위·목록 위치·반응 수를 비교하면 검증된다.

**Acceptance Scenarios**:

1. **Given** 휴지통의 공개 발행 글, **When** [복구]를 누르면, **Then** 확인창 없이 복구되고 홈·블로그 목록의 원래 위치(맨 위가 아님)에 다시 나온다.
2. **Given** 휴지통의 비공개 글·임시글, **When** 복구하면, **Then** 각각 비공개 발행 글·임시글로 돌아온다.
3. **Given** 복구한 글, **When** 상세를 보면, **Then** 댓글·좋아요·태그·사진·수정 중 작업본이 삭제 전과 같다.
4. **Given** 휴지통에 없는 글, **When** 복구를 요청하면, **Then** "찾을 수 없음"이다.
5. **Given** 작성자의 휴지통, **When** 목록을 열면, **Then** 본인 글만 최근에 지운 순으로 20개씩 보이고, 각 글에 삭제 일자와 완전 삭제까지 남은 날(예: "27일 뒤 완전 삭제")이 보인다.

---

### User Story 3 - 휴지통 글은 30일 뒤 또는 영구 삭제로 완전히 사라진다 (Priority: P2)

휴지통에 30일 동안 있던 글은 자동으로 완전히 삭제된다. 작성자는 그 전에 [영구 삭제]로 직접 완전 삭제할 수도 있다. 완전 삭제되면 그 글에 달린 댓글(남이 쓴 것 포함)·좋아요·태그 연결이 함께 지워지고, 그 글에서만 쓰던 사진은 사진 정리 대상이 된다.

**Why this priority**: 데이터가 쌓이지 않게 하는 정리 약속이다. 삭제·복구가 먼저 동작해야 의미가 있으므로 P2.

**Independent Test**: 삭제 일자를 30일 전으로 둔 글과 영구 삭제한 글을 준비해 자동 정리 후 글·댓글·좋아요·태그 연결·사진 상태를 확인하면 검증된다.

**Acceptance Scenarios**:

1. **Given** 휴지통의 글, **When** [영구 삭제]를 누르면, **Then** "영구 삭제하면 되돌릴 수 없어요. 댓글·좋아요도 함께 지워져요" 확인창 뒤 즉시 완전 삭제된다.
2. **Given** 휴지통에 들어간 지 30일이 지난 글, **When** 매일 자동 정리가 돌면, **Then** 그 글과 댓글(남이 쓴 것 포함)·좋아요·태그 연결·작업본이 완전히 지워진다.
3. **Given** 완전 삭제된 글이 쓰던 사진, **When** 그 사진을 다른 글이 쓰지 않으면, **Then** 사진 정리 대상이 되고, 다른 글이 쓰면 유지된다.
4. **Given** 완전 삭제된 글에 붙어 있던 태그, **When** 정리 후 태그를 보면, **Then** 태그 자체는 남아 다른 글이 다시 쓸 수 있다.
5. **Given** 휴지통에 없는(정상) 글, **When** 영구 삭제를 요청하면, **Then** "찾을 수 없음"이고 글은 그대로다.
6. **Given** 완전 삭제된 글의 번호·주소, **When** 새 글을 만들면, **Then** 그 번호·주소는 재사용되지 않는다.

---

### User Story 4 - 빈 임시글은 쌓이지 않는다 (Priority: P2)

제목·본문이 모두 빈 임시글은 보관할 이유가 없다. 작성자가 지우면 휴지통을 거치지 않고 바로 완전 삭제되고, [새 글]만 누르고 방치된 빈 임시글은 자동으로 정리된다.

**Why this priority**: 관리 화면과 휴지통이 의미 없는 빈 글로 가득 차는 것을 막는다. 핵심 삭제 흐름 뒤에 붙는 보조 규칙이다.

**Independent Test**: 빈 임시글을 직접 삭제하고, 24시간 넘게 방치된 빈 임시글을 준비해 자동 정리 후 결과를 확인하면 검증된다.

**Acceptance Scenarios**:

1. **Given** 제목·본문이 모두 빈 임시글, **When** 작성자가 삭제하면, **Then** 휴지통에 들어가지 않고 바로 완전 삭제되며 "빈 글이라 바로 삭제했어요" 안내가 보인다.
2. **Given** 만든 지와 마지막 수정 후 모두 24시간이 지났고 제목·본문이 비어 있으며 진행 중인 자동 저장분도 없는 임시글, **When** 매일 자동 정리가 돌면, **Then** 완전 삭제된다.
3. **Given** 제목·본문은 비었지만 아직 자동 저장 중인 내용이 남아 있거나 24시간이 지나지 않은 임시글, **When** 자동 정리가 돌면, **Then** 지워지지 않는다.

---

### User Story 5 - 남의 글은 지우거나 되살릴 수 없다 (Priority: P1)

다른 사람의 글에 대한 삭제·복구·영구 삭제 요청은 어떤 경로로 보내도 "찾을 수 없음"이고 글은 바뀌지 않는다. 관리자도 남의 글을 삭제하지 않고 숨김만 쓴다.

**Why this priority**: 삭제는 되돌릴 수 없는 데이터 손실로 이어질 수 있어 소유 검사가 깨지면 피해가 크다.

**Independent Test**: 다른 회원·관리자·비회원 자격으로 남의 글 삭제·복구·영구 삭제를 요청하고 응답과 글 상태를 확인하면 검증된다.

**Acceptance Scenarios**:

1. **Given** 다른 회원의 글, **When** 회원이나 관리자가 삭제·복구·영구 삭제를 요청하면, **Then** "찾을 수 없음"이고 요청 전후 글이 같다.
2. **Given** 비회원, **When** 삭제를 요청하면, **Then** 로그인 필요 응답을 받는다.
3. **Given** 이메일 인증 전 회원, **When** 자기 글을 삭제·복구·영구 삭제하면, **Then** 허용된다.

---

### Edge Cases

- 삭제와 복구, 또는 영구 삭제와 복구가 동시에 들어와도 한 글의 처리는 차례로 이루어져 중간 상태가 남지 않는다.
- 보는 사람의 화면에 이미 떠 있던 카드의 글이 삭제되면, 카드는 남지만 누르면 "찾을 수 없음"이다(목록의 다음 페이지에 중복·누락은 없다).
- 삭제 직후 자동 저장 요청이 들어와도 "찾을 수 없음"으로 거절되고 휴지통 글 내용은 바뀌지 않는다.
- 휴지통에서 완전 삭제까지 남은 날은 삭제 일자 + 30일 기준으로 계산한다.
- 자동 정리는 여러 서버에서 동시에 돌지 않고 한 곳에서만 실행되며, 한 번에 일정량씩 나누어 처리한다.
- 정지된 회원은 로그인할 수 없으므로 정지 기간에는 자기 글도 지울 수 없다.
- 탈퇴로 인한 글 일괄 완전 삭제는 탈퇴 spec이 이 spec의 완전 삭제 규칙을 재사용한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Users MUST be able to 자기 임시글·발행 글을 확인창을 거쳐 휴지통으로 옮길 수 있어야 한다.
- **FR-002**: System MUST 휴지통으로 옮길 때 글의 상태(임시·발행)·공개 범위·최초 공개 시점을 바꾸지 않고 "삭제됨" 표시와 삭제 일자만 더해야 한다.
- **FR-003**: System MUST 휴지통 글을 즉시 모든 상세(작성자 포함)·목록·검색·sitemap·글 수 집계에서 제외하고, 그 글의 댓글·좋아요도 함께 보이지 않게 해야 한다.
- **FR-004**: System MUST 휴지통에 있는 동안 댓글·좋아요·태그 연결·사진 연결·작업본·반응 수를 보존해야 한다.
- **FR-005**: System MUST 휴지통 글에 대한 저장·자동 저장·발행·공개 범위 변경 요청을 작성자라도 "찾을 수 없음"으로 거절해야 한다.
- **FR-006**: System MUST 휴지통으로 옮기기 직전까지 자동 저장된 내용을 잃지 않고 보존해야 한다.
- **FR-007**: System MUST 이미 휴지통에 있는 글의 삭제 요청을 아무것도 바꾸지 않고 성공으로 처리해야 한다.
- **FR-008**: Users MUST be able to 휴지통의 자기 글을 확인창 없이 복구할 수 있어야 하며, System MUST 복구된 글의 상태·공개 범위·최초 공개 시점·목록 위치·댓글·좋아요·태그를 삭제 전과 같게 해야 한다.
- **FR-009**: Users MUST be able to 휴지통의 자기 글을 확인창을 거쳐 즉시 영구 삭제할 수 있어야 하며, 휴지통에 없는 글의 영구 삭제·복구 요청은 "찾을 수 없음"이어야 한다.
- **FR-010**: System MUST 휴지통에 들어간 지 30일이 지난 글을 매일 자동으로 완전 삭제해야 한다.
- **FR-011**: System MUST 완전 삭제 시 그 글의 댓글(다른 사람이 쓴 것 포함)·좋아요·태그 연결·사진 연결·작업본을 함께 지우고, 태그 자체는 남겨야 한다.
- **FR-012**: System MUST 완전 삭제된 글에서만 쓰던 사진을 사진 정리 대상으로 표시하고, 다른 글에서도 쓰는 사진은 유지해야 한다.
- **FR-013**: System MUST 제목과 본문이 모두 빈 임시글의 삭제 요청은 휴지통을 거치지 않고 바로 완전 삭제하고, 그렇게 처리했음을 사용자에게 알려야 한다.
- **FR-014**: System MUST 매일 한 번, 제목·본문이 모두 비어 있고 생성 후와 마지막 수정 후 모두 24시간이 지났으며 진행 중인 자동 저장분이 없는 임시글을 완전 삭제해야 한다.
- **FR-015**: System MUST 삭제·복구·영구 삭제를 작성자 본인에게만 허용하고, 남의 글에 대한 요청은 관리자를 포함해 "찾을 수 없음"으로 거절하며 글을 바꾸지 않아야 한다. 비회원은 로그인 필요 응답을 받는다.
- **FR-016**: System MUST 이메일 인증 전 회원에게도 자기 글의 삭제·복구·영구 삭제를 허용해야 한다.
- **FR-017**: System MUST 한 글에 대한 삭제·복구·영구 삭제를 차례로 처리해 동시 요청에도 결과가 일관되게 해야 한다.
- **FR-018**: System MUST 휴지통 목록을 본인 글만, 최근 삭제 순으로, 20개씩 이어 보기 방식으로 제공하고, 각 항목에 삭제 일자와 완전 삭제 예정일(남은 날)을 보여야 한다.
- **FR-019**: System MUST 완전 삭제된 글의 번호와 주소를 재사용하지 않아야 한다.
- **FR-020**: System MUST 자동 정리 작업이 여러 서버에서 중복 실행되지 않게 하고, 한 번에 일정량씩 나누어 처리해야 한다.

### Key Entities *(include if feature involves data)*

- **글 (post)**: 상태·공개 범위와 별개로 "삭제됨" 여부와 삭제 일자를 가진다. 삭제 일자 + 30일이 완전 삭제 예정일이다.
- **글 부속 데이터**: 댓글(comment), 좋아요(post_like), 태그 연결(post_tag), 사진 연결(post_image), 수정 작업본(post_draft). 휴지통 동안 보존되고 완전 삭제 때 함께 지워진다.
- **태그 (tag)**: 글이 완전 삭제돼도 남는다.
- **사진 (image)**: 완전 삭제된 글에서만 쓰이던 사진은 "연결 끊김" 상태가 되어 사진 정리 작업의 대상이 된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 삭제 직후 모든 노출 위치(상세·홈·블로그·태그·검색·sitemap·글 수) 점검에서 삭제된 글 노출이 0건이고, 휴지통 목록에서만 보인다.
- **SC-002**: 복구한 글의 상태·공개 범위·목록 위치·댓글 수·좋아요 수가 삭제 전과 100% 같다.
- **SC-003**: 30일 경과 또는 영구 삭제 후 그 글과 댓글·좋아요·태그 연결 데이터가 0건 남고, 다른 글이 쓰지 않는 사진은 100% 정리 대상이 된다.
- **SC-004**: 빈 임시글 삭제는 100% 휴지통을 거치지 않고, 24시간 넘게 방치된 빈 임시글은 다음 자동 정리 후 0건 남는다.
- **SC-005**: 남의 글에 대한 삭제·복구·영구 삭제 요청은 100% "찾을 수 없음"이며 요청 전후 글 데이터가 같다.
- **SC-006**: 작성자는 삭제·복구를 각각 두 번 이내의 조작(버튼 + 확인)으로 끝낸다.
- **SC-007**: 휴지통의 모든 글에 완전 삭제까지 남은 날이 표시된다.

## Assumptions

- 내 글 관리 화면의 휴지통 탭 배치·문구·개수 표시는 010-manage-posts에서 다루며, 이 spec은 삭제·복구·영구 삭제 동작과 휴지통 목록 데이터 규칙을 정한다.
- 공개 노출 조건(삭제 제외 포함)과 읽기 판정은 006-post-visibility의 공통 판정을 재사용한다.
- 사진 파일의 실제 삭제 시점은 사진 정리 작업(004-image-upload) 규칙을 따른다. 이 spec은 정리 대상 표시까지만 책임진다.
- 회원 탈퇴의 30일 유예·익명 처리는 이 spec의 범위 밖이며 021-member-withdraw에서 다룬다(완전 삭제 규칙은 재사용).
- 관리자의 글 처리는 삭제가 아니라 숨김이며, 신고·숨김 spec(020-report-hide)에서 다룬다.
- 30일 보관 기간과 24시간 빈 임시글 기준은 팀 공통 결정 값이다.
- 휴지통 검색·일괄 복구·일괄 삭제, 탈퇴 전 글 내보내기는 개인 확장으로 범위 밖이다.
