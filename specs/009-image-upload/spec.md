# Feature Specification: 사진 업로드 (009-image-upload)

**Feature Branch**: `009-image-upload`

**Created**: 2026-10-07

**Status**: Draft

**Input**: User description: "작성자는 에디터에 사진을 붙여 넣거나 끌어 놓아 바로 올리고, 본문에는 사진 주소만 남는다. 사진은
올리기 전에 가볍게 줄이고 촬영 위치 같은 사진 속 정보를 지우며, 목록 카드용 작은 썸네일도 함께 만든다. 업로드가 끝나지 않은

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 에디터에 사진을 넣고 발행한다 (Priority: P1)

작성자가 에디터에 사진을 붙여 넣거나 끌어 놓으면 사진이 바로 올라가고, 본문에는 그 사진의 주소가 들어간다. 발행하면 독자는
본문에서 사진을 보고, 목록 카드에는 본문 첫 사진의 작은 썸네일이 대표 이미지로 보인다.

**Why this priority**: 개발 글은 화면 캡처·그래프 없이 설명하기 어렵다. 사진이 들어가야 글쓰기 기능이 완성되고, 목록 카드의
썸네일 자리도 이때 처음 채워진다.

**Independent Test**: 휴대폰 사진(위치 정보 포함, 수 MB)을 에디터에 붙여 넣고 발행해, 본문에 사진이 보이는지, 받은 파일에
위치 정보가 없고 크기가 줄었는지, 홈 카드에 그 사진의 썸네일이 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 작성자가 에디터를 엶, **When** jpg·png·gif·webp 사진(10MB 이하)을 붙여 넣거나 끌어 놓으면, **Then**
   업로드가 진행되는 동안 임시 표시가 보이고, 끝나면 본문에 사진 주소가 들어가며 미리보기에 사진이 보인다.
2. **Given** 긴 변이 1920px을 넘는 사진, **When** 올리면, **Then** 긴 변 1920px 이하로 줄어든 가벼운 사진이 저장되고, 촬영
   위치 같은 사진 속 정보는 남지 않는다.
3. **Given** 사진을 올림, **When** 업로드가 끝나면, **Then** 가로 640px 이하의 목록 카드용 썸네일도 함께 저장된다.
4. **Given** 본문에 내가 올린 사진이 여러 장, **When** 발행하면, **Then** 본문에 처음 나오는 내가 올린 사진의 640px 썸네일이
   목록 카드의 대표 이미지가 되고, 글 상세와 링크 미리보기에는 원본이 쓰인다.
5. **Given** 본문에 사진이 없음, **When** 발행하면, **Then** 대표 이미지는 비어 있고 카드에는 빈 썸네일 자리가 보인다.
6. **Given** 확장자만 바꾼 다른 형식의 파일, 손상된 파일, 해상도가 지나치게 큰 파일(예: 1만 px 초과), **When** 올리면,
   **Then** 업로드가 거부되고 저장소에 남은 파일은 지워진다.
7. **Given** 비회원, **When** 사진 업로드를 요청하면, **Then** 거부된다.

### User Story 2 - 업로드가 끝나지 않은 사진은 발행되지 않는다 (Priority: P2)

네트워크가 끊기거나 업로드가 실패해도 작성자는 사진이 들어간 채로 계속 쓸 수 있다. 사진은 이 기기에 보관되어 있다가 연결되면
자동으로 다시 올라간다. 다만 아직 올라가지 않은 사진이 본문에 남아 있으면 발행은 거부된다.

**Why this priority**: 다른 사람이 볼 수 없는 주소가 공개 글에 들어가는 것을 막아야 한다. 업로드 자체(P1)가 먼저 있어야 의미가
있다.

**Independent Test**: 오프라인 상태에서 사진을 붙여 넣고 글을 이어 쓴 뒤 발행을 눌러 거부되는지, 연결을 복구하면 사진이 자동으로
올라가 본문 주소가 진짜 주소로 바뀌고 발행되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 오프라인이거나 업로드가 실패함, **When** 사진을 넣으면, **Then** 사진은 이 기기에 보관되고 본문에는 "업로드 대기"
   임시 표시가 들어가며, 에디터 화면에는 사진이 정상으로 보인다.
2. **Given** 업로드 대기 사진이 있음, **When** 자동 저장 시점이 되면, **Then** 글은 그대로 저장된다(글이 사라지지 않게).
3. **Given** 업로드 대기 사진이 있음, **When** 연결이 돌아오면, **Then** 자동으로 다시 올리고 성공하면 임시 표시가 진짜 사진
   주소로 바뀐다.
4. **Given** 본문에 업로드 대기 사진이 남아 있음, **When** 발행하면, **Then** 발행되지 않고 "업로드가 끝나지 않은 사진이
   있어요" 이유가 다른 검증 실패와 함께 한 번에 표시되며 글은 임시글로 남는다.

### User Story 3 - 사진에 대체글을 넣는다 (Priority: P3)

사진을 볼 수 없는 독자를 위해 작성자는 발행 설정 창에서 사진마다 대체글을 넣을 수 있다. 넣지 않아도 발행은 막지 않는다.

**Why this priority**: 접근성을 높이지만 강제하면 글쓰기가 번거로워진다. 업로드·발행이 먼저다.

**Independent Test**: 대체글 없는 사진 2장이 든 글의 발행 설정 창에서 안내가 뜨는지, 한 장에만 대체글을 넣고 발행해 본문에
반영되는지, 나머지 사진은 화면 낭독기가 건너뛰는 빈 대체글로 그려지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사진을 넣음, **When** 본문에 들어가면, **Then** 대체글 자리는 비어 있고 원래 파일 이름은 들어가지 않는다.
2. **Given** 대체글이 빈 사진이 2장 있는 글, **When** 발행 설정 창을 열면, **Then** "대체글이 없는 사진이 2장 있어요
   [대체글 넣기]" 안내가 보이고, 누르면 사진마다 작은 미리보기와 입력칸, "사진을 볼 수 없는 분께 읽어 줄 설명이에요" 안내가
   보인다.
3. **Given** 입력칸에 대체글을 씀, **When** 발행하면, **Then** 그 사진의 대체글이 본문 원문에 반영되어 보인다.
4. **Given** 대체글이 빈 사진, **When** 발행하면, **Then** 발행은 막히지 않고 사진은 화면 낭독기가 꾸밈 이미지로 건너뛰는 빈
   대체글로 그려진다.
5. **Given** 대체글이 125자를 넘음, **When** 입력하면, **Then** 거부하지 않고 짧게 쓰라는 안내만 보인다.

### User Story 4 - 움직이는 GIF를 올린다 (Priority: P4)

작성자는 동작을 보여주는 GIF를 변환 없이 그대로 올린다. 독자에게는 처음에 첫 장면과 재생 표시(▶)가 보이고, 누르면 움직인다.

**Why this priority**: 개발 글에서 화면 동작을 보여줄 때 쓰이지만 일반 사진보다 빈도가 낮다.

**Independent Test**: 1920px·300장 이하의 GIF를 올려 발행하고, 본문에 정지 장면 + ▶가 보이는지, 누르면 재생되고 다시 누르면
멈추는지, 스크립트가 꺼진 브라우저에서 누르면 원본이 새 탭에서 열리는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 가로·세로 각 1920px 이하, 프레임 300장 이하의 GIF, **When** 올리면, **Then** 원본은 줄이거나 변환하지 않고 그대로
   저장되며 썸네일은 첫 장면으로 만들어진다.
2. **Given** 가로나 세로가 1920px을 넘는 GIF, **When** 고르면, **Then** 고르는 순간 "GIF는 가로·세로 1920px까지 올릴 수
   있어요"가 보인다. 화면 검사를 우회해 올려도 업로드 완료 확인에서 거부되고 파일이 지워진다.
3. **Given** 프레임이 300장을 넘는 GIF, **When** 올리면, **Then** 업로드 완료 확인에서 거부되고 파일이 지워진다.
4. **Given** GIF가 든 발행 글, **When** 독자가 보면, **Then** 처음엔 첫 장면 정지 이미지와 ▶ 표시가 보이고, 누르거나 키보드
   Enter를 누르면 재생되며 다시 누르면 정지 장면으로 돌아간다.
5. **Given** 스크립트가 동작하지 않는 환경, **When** 정지 이미지를 누르면, **Then** 원본 GIF가 새 탭에서 열린다.
6. **Given** 움직이는 webp·png, **When** 올리면, **Then** 첫 장면만 남는다는 안내가 업로드 화면에 있고 정지 사진으로 저장된다.

### User Story 5 - 내 사진 저장 공간을 확인한다 (Priority: P5)

한 사람이 저장소를 채우지 않도록 사진 저장 공간은 1인 1GB, 하루 200장으로 제한된다. 작성자는 설정 화면에서 사용량을 보고,
한도에 가까워지거나 넘으면 에디터에서 안내를 받는다.

**Why this priority**: 서비스 운영을 지키는 장치지만 보통 사용자는 거의 닿지 않는 한도다.

**Independent Test**: 사용량을 한도 근처로 맞춘 계정으로 여러 장을 동시에 올려 1GB를 넘지 않는지, 하루 201번째 사진이
거부되는지, 설정 화면에 사용량 막대가 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 회원, **When** 설정 화면을 열면, **Then** "사진 저장 공간 312MB / 1GB" 같은 막대와 "지운 사진의 공간은
   7일 뒤 돌아와요" 안내가 보인다.
2. **Given** 지금 사용량 + 올릴 사진(원본 + 썸네일) 크기가 1GB를 넘음, **When** 올리면, **Then** 업로드가 시작되지 않고
   "사진 저장 공간(1GB)을 다 썼어요. 쓰지 않는 사진이 든 글을 지우면 7일 뒤 공간이 돌아와요"가 보인다.
3. **Given** 한도 직전의 회원, **When** 여러 장을 동시에 올리면, **Then** 합계가 1GB를 넘는 업로드는 하나도 받아들여지지
   않는다.
4. **Given** 오늘(한국 시간 0시 기준) 이미 200장을 올림, **When** 한 장 더 올리면, **Then** "오늘은 사진을 200장까지 올릴 수
   있어요. 내일 다시 시도해 주세요"가 보인다.
5. **Given** 사용량이 90%를 넘음, **When** 에디터를 열면, **Then** 사진 버튼 옆에 "남은 공간 약 100MB" 같은 안내가 보인다.

### User Story 6 - 쓰지 않는 사진은 자동으로 정리된다 (Priority: P6)

올렸지만 글에 쓰지 않은 사진과, 글에서 빠진 사진은 일정 기간 뒤 저장소에서 자동으로 지워지고 그만큼 저장 공간이 돌아온다.

**Why this priority**: 저장소가 버려진 파일로 차는 것을 막지만, 사용자가 직접 보는 기능은 아니다.

**Independent Test**: 올리기만 하고 쓰지 않은 사진, 발행 글에서 뺀 사진을 시간을 앞당겨 정리 시점에 두고, 각각 정해진 기간이
지나야만 지워지는지, 현재 프로필 사진은 지워지지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 업로드만 하고 어떤 글에도 연결되지 않은 사진, **When** 24시간이 지난 뒤 정리 시점이 되면, **Then** 원본·썸네일
   파일과 기록이 지워진다.
2. **Given** 저장·발행으로 글에 연결되었다가 본문에서 빠진 사진, **When** 빠진 지 7일이 지난 뒤 정리 시점이 되면, **Then**
   원본·썸네일 파일과 기록이 지워지고 그만큼 저장 공간이 돌아온다.
3. **Given** 글을 지움, **When** 바로 사용량을 보면, **Then** 공간은 즉시 돌아오지 않고 정리가 파일을 실제로 지울 때 돌아온다.
4. **Given** 현재 쓰고 있는 프로필 사진, **When** 정리 시점이 되면, **Then** 지워지지 않는다.
5. **Given** 저장소 삭제가 실패함, **When** 정리가 끝나면, **Then** 기록은 남아 다음 정리 때 다시 시도된다.

---

### Edge Cases

- 남이 올린 사진 주소를 내 본문에 붙여 넣고 발행하면? → 내 글에 연결되지 않고 이미지가 아니라 링크로 보인다. 그 사진은 내
  저장 공간에 세지 않고, 원래 주인의 글에서는 그대로 보이며, 내 글 때문에 정리 대상이 되지도 않는다.
- 남이 올린 사진의 업로드 완료 확인을 요청하면? → 없는 사진과 똑같이 응답한다.
- 다른 환경(예: 로컬 개발) 사진 주소를 운영 글에 붙여 넣으면? → 우리 사진으로 보지 않아 외부 이미지 링크가 된다.
- 사진 공개 주소를 바꾸면? → 옛 주소로 쓴 우리 사진도 이미지로 계속 보이고, 작성자가 쓴 원문은 바뀌지 않는다.
- 업로드 허가를 받은 뒤 5분 안에 올리지 않으면? → 허가가 만료되어 다시 요청해야 한다.
- 1분에 20장을 넘게 올리면? → 잠시 뒤 다시 시도하라는 안내와 함께 거부된다.
- 실패한 업로드는 하루 200장에 세는가? → 센다(반복 요청 방지).
- 업로드를 신청할 때 알린 크기보다 실제 파일이 크면? → 거부하고 파일을 지운다.
- 썸네일이 없는 옛 사진이 첫 사진이면? → 카드에 원본 주소를 대신 쓴다.
- 비공개 글의 사진은? → 주소를 아는 사람은 볼 수 있다(주소는 추측할 수 없고 저장소 목록 조회는 막혀 있다).
- 사진 파일이 지워진 뒤에도 그 사진을 이미 본 독자의 브라우저에는 최대 1년 남을 수 있다 → 허용 한계로 둔다.
- GIF의 위치 정보 외 다른 메타데이터는? → 서버가 파일을 고치지 않으므로 남을 수 있다(알려진 한계).
- 로그아웃하면? → 이 기기에 보관된 업로드 대기 사진도 그 사용자의 작성 데이터와 함께 지워진다.

## Requirements *(mandatory)*

### Functional Requirements

**업로드 (C-IMG-1, docs/04 §4-1·§4-2, docs/10 §6)**

- **FR-001**: 사진 업로드는 로그인하고 가입을 마친 회원만 할 수 있어야 한다. 권한 판단은 docs/42 §10을 따른다.
- **FR-002**: 받는 형식은 jpg·png·gif·webp, 파일 하나 10MB 이하여야 한다. 확장자만 바꾼 파일(실제 내용과 형식이 다른 파일)은
  거부해야 한다.
- **FR-003**: 사진은 올리기 전에 브라우저에서 긴 변 최대 1920px로 줄이고 가벼운 형식으로 변환하며, 촬영 위치 같은 사진 속
  정보를 제거해야 한다. GIF는 원본을 그대로 둔다.
- **FR-004**: 사진마다 가로 최대 640px의 목록 카드용 썸네일을 함께 만들어 올려야 한다. GIF의 썸네일은 첫 장면이다.
- **FR-005**: 사진 데이터는 서비스 서버를 거치지 않고 파일 저장소로 바로 올라가야 하며, 업로드 허가는 5분만 유효해야 한다.
  저장소가 직접 업로드를 받을 수 없는 환경에서는 서버 경유 업로드로 바꾸되 규칙은 같아야 한다.
- **FR-006**: 업로드가 끝나면 서버가 원본·썸네일의 존재, 실제 크기, 실제 형식, 해상도를 다시 검사해야 한다. 썸네일은 가로
  640px·1MB 이하, 해상도가 지나치게 큰 파일은 거부하며, 실패하면 저장소의 파일을 지워야 한다.
- **FR-007**: 업로드 완료 확인은 올린 사람만 할 수 있어야 하며, 남의 사진이면 없는 사진과 같은 응답이어야 한다.
- **FR-008**: 저장 파일 이름과 경로는 서버가 정해야 하며 추측할 수 없어야 한다. 원래 파일 이름은 저장하지도, 화면 어디에도
  보여주지도 않아야 한다.
- **FR-009**: 사진 주소는 바뀌지 않으므로 독자 브라우저에 오래(1년) 보관되게 해야 한다.
- **FR-010**: 사용자당 1분에 20장까지만 업로드 허가를 내줘야 한다.

**사진 주소와 표시 (docs/23 §2-4, docs/12 S-6)**

- **FR-011**: 본문에는 사진의 전체 주소를 그대로 쓰되, "우리 사진"은 지금의 공개 주소 또는 예전에 쓴 공개 주소 목록 중 하나로
  시작하고 나머지가 저장 경로 모양일 때만으로 판별해야 한다. 판별은 한 가지 규칙으로만 한다.
- **FR-012**: 우리 사진 중 **글 작성자가 올린 사진만** 본문에서 이미지로 보여야 하고, 표시할 때 주소를 지금의 공개 주소로 바꿔
  써야 한다. 외부 이미지와 남이 올린 사진은 링크로 보여야 한다(2026-10-07 확정).
- **FR-013**: 작성자가 쓴 원문은 서버가 바꾸지 않아야 한다.
- **FR-014**: 공개 주소를 바꿀 때는 옛 주소를 목록에 남겨, 옛 글의 사진이 링크로 바뀌지 않게 해야 한다. 상세 HTML은 읽을 때
  렌더링하므로 발행 글을 다시 만들 필요는 없고 렌더링 캐시 버전만 올린다.
- **FR-015**: 비공개 글의 사진은 주소를 알면 볼 수 있다. 저장소는 파일 하나 읽기만 익명에게 허용하고, 목록 조회와 서명 없는
  쓰기는 막아야 한다.

**업로드 대기열 (docs/04 §4-3)**

- **FR-016**: 오프라인이거나 업로드에 실패한 사진은 이 기기에 보관하고, 본문에는 "업로드 대기" 임시 표시를 넣으며, 에디터
  화면에는 보관한 사진을 정상으로 보여야 한다.
- **FR-017**: 연결이 돌아오면 대기 사진을 자동으로 다시 올리고, 성공하면 임시 표시를 진짜 주소로 바꿔야 한다.
- **FR-018**: 업로드 대기 사진이 있어도 자동 저장은 계속되어야 한다.
- **FR-019**: 로그아웃할 때 그 사용자의 대기 사진도 이 기기에서 지워야 한다.

**발행 연동 (docs/05 §4·§7, docs/10 §6)**

- **FR-020**: 본문에 업로드 대기 사진이 남아 있으면 발행을 거부하고, 다른 검증 실패와 함께 한 번에 알려야 한다. 글은 임시글로
  남아야 한다.
- **FR-021**: 수동 저장·자동 저장 반영·발행 때 본문에 든 우리 사진 중 글 작성자가 올린 사진만 그 글에 연결하고, 본문에서 빠진
  사진은 연결이 끊긴 시각을 기록해야 한다. 비교는 주소 문자열이 아니라 저장 경로로 해야 한다.
- **FR-022**: 발행할 때 본문에 나오는 순서대로 사진 연결의 순서(`position`)를 기록하고, 순서 0인 사진의 640px 썸네일을 대표
  이미지로 쓴다. 사진이 없으면 대표 이미지는 비고, 썸네일이 없는 옛 사진이면 원본을 쓴다. 대표 이미지 주소는 글에 저장하지 않는다.
- **FR-023**: 글 상세와 링크 미리보기에는 원본을, 목록 카드에는 썸네일을 써야 한다. 카드 썸네일의 대체글은 글 제목이다.
- **FR-024**: 요약을 만들 때 사진은 빼야 한다(002 FR-020과 같다).

**대체글 (I-3, docs/23 §4)**

- **FR-025**: 사진을 본문에 넣을 때 대체글 자리를 비워 두고, 원래 파일 이름을 넣지 않아야 한다.
- **FR-026**: 발행 설정 창은 대체글이 빈 사진의 수를 알리고, 사진마다 미리보기와 입력칸을 제공해 입력한 값을 본문 원문에
  반영해야 한다.
- **FR-027**: 대체글이 없어도 발행을 막지 않아야 한다. 빈 대체글은 화면 낭독기가 건너뛰는 빈 값으로 그려야 한다(대체글 속성을
  빼지 않는다). 125자 초과는 안내만 한다.
- **FR-028**: 프로필 사진은 옆에 닉네임이 있으므로 빈 대체글로 그린다.

**GIF (I-4, docs/23 §5)**

- **FR-029**: GIF는 줄이거나 변환하지 않고 그대로 올리며, 가로·세로 각 1920px 이하, 프레임 300장 이하여야 한다. 고를 때 화면에서
  먼저 안내하고, 업로드 완료 확인에서 파일 전체를 풀지 않고 다시 검사해 넘으면 거부·삭제해야 한다.
- **FR-030**: 본문의 GIF는 처음엔 첫 장면 썸네일을 원래 크기로 보여주고 ▶ 표시를 붙이며, 누르면(키보드 Enter 포함) 원본이
  재생되고 다시 누르면 정지 장면으로 돌아가야 한다. 스크립트가 없으면 누를 때 원본이 새 탭에서 열려야 한다.
- **FR-031**: 재생 기능은 우리 서버의 스크립트로만 동작해야 하며, 본문 정화 허용 목록을 넓히지 않아야 한다.
- **FR-032**: GIF 링크 이름은 대체글이고, 대체글이 비었으면 "움직이는 이미지 재생"이어야 한다. 카드 썸네일은 첫 장면, 링크
  미리보기는 원본이다.
- **FR-033**: 움직이는 webp·png는 첫 장면만 남는다는 안내를 업로드 화면에 보여야 한다.

**사용자별 저장 공간 (I-2, docs/23 §3)**

- **FR-034**: 사진 저장 공간은 1인 1GB, 하루 200장(한국 시간 0시 기준)이며 둘 다 설정값이어야 한다.
- **FR-035**: 사용량은 그 사람이 올린 모든 사진(업로드만 한 것, 글에 연결된 것, 연결이 끊겨 정리를 기다리는 것, 프로필 사진
  포함)의 원본 + 썸네일 크기 합이어야 한다. 남이 올린 사진은 내 사용량에 세지 않는다.
- **FR-036**: 업로드 허가를 내줄 때 "지금 사용량 + 이번에 올릴 원본·썸네일 크기"로 검사해야 하며, 여러 장을 동시에 요청해도
  합계가 한도를 넘지 않아야 한다.
- **FR-037**: 하루 장수는 업로드 허가를 내줄 때 세며, 실패한 업로드도 1장으로 센다.
- **FR-038**: 업로드 완료 때 실제 크기를 기록하고, 신고한 크기보다 크면 거부·삭제해야 한다.
- **FR-039**: 공간은 정리가 파일을 실제로 지울 때 돌아와야 한다.
- **FR-040**: 설정 화면에 사용량 막대와 안내, 에디터에 한도 초과·하루 장수 초과·90% 초과 안내를 보여야 한다. 본인은 사용량,
  한도, 오늘 올린 장수, 하루 한도를 조회할 수 있어야 한다.

**정리 (docs/04 §4-4, docs/23 §6)**

- **FR-041**: 매일 새벽 정리에서 업로드만 하고 24시간이 지난 사진, 글에서 빠진 지 7일이 지난 사진의 원본·썸네일 파일을 지운 뒤
  기록을 지워야 한다. 저장소 삭제가 실패하면 기록을 남겨 다음 정리에서 다시 시도해야 한다.
- **FR-042**: 현재 쓰고 있는 프로필 사진은 지우지 않아야 한다.
- **FR-043**: 회원 탈퇴의 30일 처리 때 그 회원이 올린 사진을 모두 정리 대상으로 표시하고 프로필 사진 연결을 해제해야 하며, 파일은
  다음 정리 때 지워져야 한다(2026-10-07 확정: "연결 끊긴 지 7일"이 아니라 다음 정리 때).
- **FR-044**: 지운 사진은 저장소에서 즉시 더 이상 열리지 않아야 한다.

**저장소 점검 (I-1, docs/23 §2)**

- **FR-045**: 파일 저장소는 서비스 전용 열쇠(올리기·읽기·지우기만)로만 쓰고, 사진은 정해진 경로 아래에만 두며, 관리 화면은
  외부에 열지 않아야 한다.
- **FR-046**: 직접 업로드는 우리 사이트에서 오는 요청만 허용하고 다른 출처는 거부해야 한다.
- **FR-047**: 정상 업로드는 성공하고, 서명 위조·서명 뒤 경로 변경·서명과 다른 형식·만료된 허가·서명 없는 익명 쓰기·익명 목록
  조회·정해진 경로 밖 익명 읽기는 거부되며, 정해진 경로의 파일 하나는 익명으로 읽을 수 있어야 한다(docs/23 §2-3의 11가지).
  이 점검은 로컬 개발 저장소와 운영 저장소 두 곳 모두에서 통과해야 하며, 저장소 버전·정책·열쇠 권한을 바꿀 때 다시 돌린다.

### Key Entities *(include if feature involves data)*

- **리소스(Resource) + 사진 리소스(ResourceImage)**: 올린 사람, 종류(사진), 저장 경로, 형식, 크기, 연결 해제 일자 + 사진 전용
  속성(가로·세로, 썸네일 경로·크기). 용도(글·프로필)와 상태(업로드만 됨·연결됨)는 저장하지 않고 연결 행이 있는지로 판단한다.
- **프로필 사진(MemberProfileImage)**: 회원당 지금 프로필 사진 하나.
- **글 사진 연결(PostImage)**: 어떤 글이 어떤 사진을 어떤 순서로 쓰는지. 글 작성자가 올린 사진만 연결된다. 정리와 대표 이미지(순서 0)에 쓴다.
- **글(Post)**: 002에서 정의. 대표 이미지는 사진 연결에서 구하므로 글에 저장하지 않는다.
- **업로드 대기 사진(브라우저 보관)**: 아직 올라가지 않은 사진 원본과 본문의 임시 표시. 그 사용자·그 글에 묶인다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 일반적인 휴대폰 사진(3~8MB)이 올라간 뒤 약 0.3~0.5MB가 되고, 받은 파일에 촬영 위치 정보가 0건이다.
- **SC-002**: 목록 첫 화면 카드 9장의 썸네일 전송량이 원본 대비 약 10분의 1(약 0.4MB)이다.
- **SC-003**: 사용량이 한도 직전인 회원이 동시에 10장을 요청해도 사용량이 1GB를 넘는 경우가 0건이다.
- **SC-004**: 업로드 대기 사진이 든 글이 발행되는 경우가 0건이다.
- **SC-005**: 남이 올린 사진 주소를 넣고 발행해도 그 사진이 내 글에 연결되거나, 정리되거나, 원래 주인의 글에서 사라지는 경우가
  0건이다.
- **SC-006**: 공개 주소를 바꾸고 다시 만든 뒤에도 옛 주소로 쓴 우리 사진이 링크로 바뀌는 경우가 0건이다.
- **SC-007**: 오프라인에서 넣은 사진이 연결 복구 뒤 사용자의 추가 조작 없이 진짜 주소로 바뀐다.
- **SC-008**: 저장소 점검 11가지가 로컬과 운영 저장소 모두에서 통과한다(운영은 배포 전).
- **SC-009**: docs/23 §7의 공통 완료 기준 10가지와 docs/05 §10 6·9번(업로드 미완료 사진, 남이 올린 사진)이 모두 자동 테스트로
  확인된다.

## Assumptions

- **A-1**: 업로드 대기열은 이 기기에 작성 내용을 남기는 기능(docs/04 §2-2, 002 A-1에서 MVP 직후로 미룸)을 바탕으로 한다. 그
  기능이 아직 없으면 실패한 사진은 에디터에 남겨 [다시 시도]로 올리고, 발행 차단(FR-020)은 그대로 적용한다.
- **A-2**: 파일 저장소 제품은 팀 결정(2026-10-06, 2026-10-07 회의 확인)을 따른다. 운영 저장소의 정책·출처 허용 설정 가능 여부와
  서비스 전용 열쇠 발급은 배포 담당이 배포 전에 확인한다(미결). 직접 업로드를 설정할 수 없으면 서버 경유 업로드로 바꾼다.
- **A-3**: 프로필 사진 변경(256×256, C-AUTH-2)은 이 spec의 범위가 아니다. 다만 들어오면 같은 업로드·사용량·정리 규칙을 쓴다.
- **A-4**: 회원 탈퇴 기능 자체는 이 spec의 범위가 아니며, FR-043은 탈퇴 처리가 들어올 때 이 기능이 맡을 단계다.
- **A-5**: CDN 사용과 지운 사진의 CDN 무효화는 개인 확장이며 범위 밖이다. 공통 기간에는 저장소 공개 주소를 그대로 쓴다.
- **A-6**: 지운 사진이 이미 본 독자의 브라우저에 남는 것은 허용 한계다. "탈퇴 뒤 사진이 남지 않는다"는 저장소 기준이다.
- **A-7**: 썸네일 비율·빈 썸네일 색 같은 표시 방식은 각자 자유다(docs/10 O5). 640px 썸네일 생성은 공통이다.
