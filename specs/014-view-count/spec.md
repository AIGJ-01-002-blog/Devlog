## User Scenarios & Testing *(mandatory)*

### User Story 1 - 실제로 본 조회만 한 번씩 센다 (Priority: P1)

독자가 글 상세를 화면에 보이는 상태로 1초 이상 보면 조회가 한 번 기록된다. 같은 방문자가 같은 글을 기간(기본 24시간) 안에 새로고침해도 설정한 횟수(기본 1번)를 넘게 세지 않는다.

**Why this priority**: "새로고침으로 부풀지 않는다"가 C-VIEW-1의 정의다. 트렌딩 점수의 재료라 정확도가 중요하다.

**Independent Test**: 같은 방문자로 한 글을 5번 새로고침하고 다른 방문자 2명이 1번씩 본 뒤 반영된 조회수가 3인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 방문자 v1, v2, v3, **When** v1이 글A를 5번 새로고침하고 v2·v3이 1번씩 봄, **Then** 반영 후 글A 조회수는 3이다.
2. **Given** 로그인한 회원, **When** 다른 기기에서 같은 글을 3번 봄, **Then** 1번만 센다 (회원은 기기가 달라도 같은 사람).
3. **Given** 같은 방문자가 같은 글에 동시에 50번 기록을 요청, **When** 처리됨, **Then** 1번만 센다.
4. **Given** 중복 기준을 "30분에 5회"로 설정, **When** 같은 방문자가 기간 안에 7번 봄, **Then** 5번 센다.
5. **Given** 기간이 지난 뒤, **When** 같은 방문자가 다시 봄, **Then** 다시 센다.
6. **Given** 글을 백그라운드 탭으로 엶, **When** 사용자가 그 탭을 보기 전, **Then** 세지 않고, 탭을 보고 1초가 지나면 센다.
7. **Given** 쿠키를 막은 비회원, **When** 같은 글을 같은 날 여러 번 봄, **Then** 그날 안에서는 같은 방문자로 판정되고, 날짜가 바뀌면 이전 날과 연결할 수 없다.

### User Story 2 - 세지 말아야 할 조회는 빼고, 셌는지는 드러내지 않는다 (Priority: P2)

작성자 본인, 봇·링크 미리보기, 브라우저 미리 불러오기, 볼 수 없는 글의 조회는 세지 않는다. 기록 요청은 셌든 안 셌든 같은 응답을 받아 규칙을 추측해 조작하기 어렵다.

**Why this priority**: 부풀림 방지와 조작 방지의 나머지 절반이다.

**Independent Test**: 작성자·봇 User-Agent·미리 불러오기 표시·볼 수 없는 글로 각각 기록을 요청하고 조회수 변화와 응답을 비교한다.

**Acceptance Scenarios**:

1. **Given** 작성자 본인이 로그인 상태, **When** 내 글을 봄, **Then** 세지 않는다.
2. **Given** 봇·링크 미리보기 이름(설정 목록)을 가진 요청, **When** 기록 요청, **Then** 세지 않는다.
3. **Given** 미리 불러오기임을 밝힌 요청, **When** 기록 요청, **Then** 세지 않는다.
4. **Given** 임시·비공개(남)·휴지통·관리자 숨김·작성자 탈퇴 신청·없는 글, **When** 기록 요청, **Then** 찾을 수 없음(404와 같은 응답)이고 세지 않는다.
5. **Given** 센 요청과 중복이라 안 센 요청, **When** 응답을 비교, **Then** 두 응답은 똑같다.
6. **Given** 같은 방문자가 1분에 60번을 넘게 기록 요청, **When** 61번째, **Then** 거부된다.

### User Story 3 - 조회가 몰리거나 장애가 나도 읽기는 막히지 않고, 조회는 1분 안에 반영된다 (Priority: P3)

조회 기록은 모아 두었다가 1분마다 글의 누적 조회수와 일별 조회수에 반영한다. 기록 저장이 실패해도 글 상세는 정상으로 열린다.

**Why this priority**: "부가 기능은 핵심을 막지 않는다" 원칙과 C-VIEW-1의 반영·유실 기준이다.

**Independent Test**: 반영 전후 조회수를 확인하고, 반영 도중 서버를 멈춘 뒤 다음 반영에서 모아 둔 조회가 사라지지 않았는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 조회가 기록됨, **When** 1분 반영 전, **Then** 누적 조회수는 아직 바뀌지 않는다. **When** 반영 후, **Then** 누적 조회수와 그날의 일별 조회수가 같은 값만큼 늘어 있다.
2. **Given** 자정 무렵의 조회, **When** 반영됨, **Then** 실제 본 날짜(한국 시간)의 일별 조회수에 들어간다.
3. **Given** 반영 도중 서버가 죽음, **When** 다음 반영이 실행됨, **Then** 남은 조회가 모두 반영되고 이미 반영한 글이 다시 더해지지 않는다(저장 확정 직후 죽은 그 글 하나의 1분치 중복만 허용).
4. **Given** 조회 기록 저장 수단이 멈춤, **When** 독자가 글 상세를 엶, **Then** 글은 정상으로 열리고(로그인 정보를 못 읽으면 비로그인으로 보일 수 있음) 그동안의 조회만 빠진다.
5. **Given** 반영 사이에 글이 완전 삭제됨, **When** 반영됨, **Then** 그 글만 건너뛰고 나머지는 정상 반영된다.
6. **Given** 91일 전·89일 전 일별 조회수, **When** 매일 보관 정리가 실행됨, **Then** 90일이 지난 것만 지워지고 누적 조회수는 그대로다.

---

### User Story 4 - 글 상세에서 조회수를 본다 (Priority: P4)

독자는 글 상세에서 "조회 1,234"와 집계 기준 안내를 본다. 목록 카드에는 조회수가 없다.

**Why this priority**: 표시는 단순하며 P1~P3가 있어야 의미가 있다.

**Independent Test**: 글 상세와 목록 카드를 열어 표시 위치·형식·안내 문구를 확인한다.

**Acceptance Scenarios**:

1. **Given** 조회수 12,345인 글, **When** 상세를 엶, **Then** "조회 1.2만"이 보이고, 숫자를 가리키거나 누르면 "같은 사람은 하루에 한 번만 세요"(설정에 맞는 문구)가 보인다.
2. **Given** 방금 내가 본 조회, **When** 화면을 봄, **Then** 화면에서 바로 +1 하지 않는다(최대 1분 늦게 반영).
3. **Given** 홈·블로그·태그 목록 카드, **When** 봄, **Then** 조회수는 표시되지 않는다.

---

### Edge Cases

- 비회원으로 보다가 로그인해서 다시 보면 1번 더 셀 수 있다 (드물어 허용).
- 기록 요청 실패는 다시 보내지 않고 화면에도 표시하지 않는다.
- 상세 화면을 여는 것 자체는 조회를 세지 않는다. 기록은 별도 요청이다.
- JS를 끈 독자는 세지 않는다.
- 반영 사이에 서버가 죽어 이름을 바꾼 처리 중 묶음이 남으면 다음 실행 때 먼저 처리한다.
- 사용자 IP는 신뢰하는 프록시가 전달한 값만 쓰고, 위조된 전달 헤더로 다른 방문자인 척할 수 없다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 글 상세가 화면에 보이는 상태로 1초 이상 지났을 때만 조회 기록 요청을 한 번 보내고, 탭이 보이지 않는 동안에는 보내지 않아야 한다.
- **FR-002**: System MUST 방문자를 회원은 회원 번호로, 비회원은 무작위 방문자 식별 쿠키로, 쿠키가 없으면 IP와 User-Agent를 날마다 바뀌는 비밀값과 함께 해시한 값으로 구분해야 한다. 원래 IP는 저장하지 않는다.
- **FR-003**: System MUST 같은 방문자·같은 글의 조회를 "처음 본 순간부터 기간(`dedupe-window`) 안에 최대 횟수(`max-per-window`)"까지만 세야 한다. 기본값은 24시간 1회이고 팀원별 설정으로 바꿀 수 있어야 한다.
- **FR-004**: System MUST 중복 판정과 기록을 원자적으로 처리해 같은 방문자의 동시 요청이 최대 횟수를 넘지 않게 해야 한다.
- **FR-005**: System MUST 작성자 본인, 설정 목록의 봇·링크 미리보기 이름을 가진 요청, 미리 불러오기임을 밝힌 요청의 조회를 세지 않아야 한다.
- **FR-006**: System MUST 지금 읽을 수 없는 글(공통 글 접근 규칙)에 대한 기록 요청을 찾을 수 없음(404와 같은 응답)으로 거부하고 세지 않아야 한다.
- **FR-007**: System MUST 기록 요청에 셌는지와 상관없이 같은 성공 응답(내용 없음)을 줘야 한다.
- **FR-008**: System MUST 같은 방문자의 기록 요청을 1분에 60번으로 제한해야 한다.
- **FR-009**: System MUST 비회원도 기록 요청을 할 수 있게 하되, 공통 요청 위조 방지 규칙을 지켜야 한다.
- **FR-010**: System MUST 기록을 모아 두었다가 1분마다 글의 누적 조회수와 일별 조회수(한국 시간 날짜)에 함께 반영해야 하며, 반영이 글의 "수정 일자"를 바꾸지 않아야 한다.
- **FR-011**: System MUST 반영 도중 서버가 멈춰도 모아 둔 조회를 잃지 않고, 이미 반영한 글을 다시 더하지 않도록 글 단위로 반영 완료를 기록해야 한다. 반영 작업은 여러 서버에서 동시에 돌지 않아야 한다.
- **FR-012**: System MUST 조회 기록 저장이 실패하거나 저장 수단이 멈춰도 기록을 건너뛰고 글 상세는 정상으로 열리게 해야 한다.
- **FR-013**: System MUST 일별 조회수를 90일 보관하고 매일 그보다 오래된 것을 지워야 한다. 누적 조회수는 계속 유지한다. 글이 완전 삭제되면 그 글의 일별 조회수도 함께 지운다.
- **FR-014**: System MUST 중복 판정용 방문자 기록을 기간이 지나면 자동으로 지우고, 방문자 식별값·IP를 로그에 남기지 않아야 한다.
- **FR-015**: System MUST 조회수를 글 상세에만 "조회 N"(1만 이상 `1.2만`, 좋아요와 같은 형식)으로 보이고, 집계 기준 안내 문구를 함께 제공하며, 목록 카드에는 보이지 않아야 한다.
- **FR-016**: System MUST 관리자 조회의 집계 여부를 정해진 규칙대로 처리해야 한다. [NEEDS CLARIFICATION: 관리자 조회 제외 — 40·42는 관리자도 제외하자고 31에 요청했으나, 31의 확정 제외 목록에는 관리자가 없음]
- **FR-017**: 개인정보 처리방침에 방문자 식별 쿠키를 "조회수 중복 방지용 무작위 식별자"로 안내해야 한다.

### Key Entities *(include if feature involves data)*

- **글 (`post`)**: 누적 조회수를 미리 가지고 있다. 트렌딩 기본 점수의 재료다.
- **일별 조회수 (`post_view_daily`)**: 글·날짜별 조회 합계. 누가 봤는지는 담지 않는다. 90일 보관.
- **방문자 중복 기록**: 방문자·글별로 기간 안에 센 횟수. 공통 데이터베이스에 두지 않고 기간이 지나면 사라진다.
- **방문자 식별 쿠키**: 비회원을 구분하는 무작위 값(1년).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 방문자가 기간 안에 새로고침하거나 동시에 요청해도 설정한 횟수(기본 1번)를 넘게 세는 경우가 0건이다.
- **SC-002**: 작성자 본인·봇·링크 미리보기·미리 불러오기·볼 수 없는 글의 조회가 세어지는 경우가 0건이다.
- **SC-003**: 조회 기록이 실패하거나 기록 저장 수단이 멈춘 동안에도 글 상세는 100% 정상으로 열린다.
- **SC-004**: 기록된 조회는 1분 안에 누적 조회수와 일별 조회수에 반영된다.
- **SC-005**: 반영 도중 서버가 멈춘 시험에서 모아 둔 조회가 사라지는 경우가 0건이다.
- **SC-006**: 센 요청과 안 센 요청의 응답을 구분할 수 있는 차이가 0건이다.
- **SC-007**: 원래 IP가 저장소·임시 저장소·로그 어디에도 0건 남는다.
- **SC-008**: 90일이 지난 일별 조회수는 다음 정리 뒤 0건 남는다.

## Assumptions

- 조회수는 장애 때 완전한 정확성을 보장하는 회계 값이 아니다. 저장 수단 장애 동안의 조회 누락과 반영 중 장애 때 글 하나의 1분치 중복은 허용한다.
- 01 결정 기록 2026-10-07(H8)에 따라 장애 시 "글 상세 정상" 약속은 비회원 기준이다(로그인 정보를 못 읽으면 비로그인으로 보일 수 있다).
- 사용자 IP 판별은 01 결정 기록 2026-10-07(H4)의 신뢰 프록시 규칙을 따른다.
- 글 읽기 판정은 공통 글 접근 규칙 하나를 따르며, 관리자 숨김 글은 그 규칙에서 볼 수 없는 글이다.
- 조회수 표시 위치와 기록 요청을 넣을 위치는 글 상세 spec과 함께 정한다.
- 트렌딩 기본 점수는 누적 조회수를 쓰고, 일별 조회수는 점수식 변경·작성자 통계 대비용이다 ([018-trending](../018-trending/spec.md)).
- 강성찬의 원안(30분 5회)은 설정값과 안내 문구만 바꿔 쓸 수 있다.
- 개인 확장(작성자 통계 화면, 블로그 방문자 수, JS 없는 독자도 세는 방식)은 범위 밖이다.
