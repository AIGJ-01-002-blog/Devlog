# Feature Specification: 팔로우·팔로잉 피드 (016-follow-feed)

**Feature Branch**: `016-follow-feed`

**Created**: 2026-10-07

**Status**: Draft

**Input**: User description: "로그인한 회원이 다른 회원을 승인 없이 한쪽 방향으로 팔로우하고, 별도 페이지 /feed에서
팔로우한 사람의 공개 글을 홈과 같은 카드로 이어 본다. 팔로워·팔로잉 수와 목록은 누구나 볼 수 있다. 상세 규칙은
docs/24-follow-feed.md를 따른다."

**관련 기능 ID**: 팔로우·구독 + 피드 (docs/01 §2-3 Tier C)

**선행 기능**: `003-read-share` (카드·9개·[더 보기] 커서 규칙, 블로그 상단, 글 상세 작성자 영역)

**우선순위 단계**: 이후 단계 (Tier C)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 읽고 싶은 사람을 팔로우한다 (Priority: P1)

로그인한 회원이 블로그 상단이나 글 상세 작성자 영역의 [팔로우]를 누르면 상대의 승인 없이 바로 팔로우되고, 다시 누르면
언팔로우된다.

**Why this priority**: 팔로우 관계가 있어야 피드와 목록이 의미를 가진다. 이것만으로도 "이 사람을 따라간다"는 가치가 생긴다.

**Independent Test**: 회원 A로 B의 블로그에서 [팔로우]를 눌러 B의 팔로워 수가 1 늘고 버튼이 [팔로잉 ✓]로 바뀌는지, 같은
요청을 동시에 20번 보내도 관계가 하나이고 "팔로우함" 사건이 한 번만 생기는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 회원 A, B의 블로그, **When** [팔로우]를 누르면, **Then** 버튼이 즉시 [팔로잉 ✓]로 바뀌고 B의 팔로워 수가
   1 늘어난다. 이메일 인증 여부와 상관없이 할 수 있다.
2. **Given** A가 B를 팔로우 중, **When** [팔로잉 ✓]에 마우스를 올리거나 초점을 주면, **Then** [언팔로우]로 바뀌고, 누르면 확인 창
   없이 언팔로우되며 다시 누르면 되돌릴 수 있다.
3. **Given** 같은 대상, **When** 팔로우 요청을 여러 번(동시에) 보내면, **Then** 관계는 하나이고 "팔로우함" 사건은 한 번만 생긴다.
   팔로우하지 않은 대상에 언팔로우를 보내도 아무것도 바뀌지 않는다.
4. **Given** 비회원, **When** [팔로우]를 누르면, **Then** 로그인 화면으로 가고 로그인 후 원래 페이지로 돌아온다.
5. **Given** 내 블로그나 내 글, **When** 열면, **Then** 팔로우 버튼이 없다. 자기 자신을 팔로우하는 요청은 규칙 위반으로 거부된다.
6. **Given** 팔로우 요청이 실패함, **When** 결과를 받으면, **Then** 버튼이 원래대로 돌아오고 "잠시 후 다시 시도해 주세요"가 보인다.
7. **Given** 없는 블로그나 탈퇴 신청한 블로그, **When** 팔로우를 요청하면, **Then** "찾을 수 없음"이다.

### User Story 2 - 팔로잉 피드에서 새 글을 본다 (Priority: P2)

회원은 상단 메뉴의 [피드]로 `/feed`에 들어가 팔로우한 사람들의 공개 글을 처음 공개된 순서의 최신순으로 9개씩 본다.

**Why this priority**: 팔로우의 실질적인 보상이지만, 팔로우 관계(P1)가 먼저 있어야 한다.

**Independent Test**: A가 B·C를 팔로우하고 B·C·D가 공개·비공개 글을 섞어 쓴 상태에서 `/feed`에 B·C의 공개 글만 최신순 9개가
보이는지, [더 보기]를 끝까지 넘겨도 중복·누락이 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 회원, **When** 상단 메뉴를 보면, **Then** [피드]가 있다. 비회원에게는 없고 `/feed`로 직접 오면 로그인 화면으로
   간다.
2. **Given** 팔로우한 사람의 글이 공개·비공개·임시·휴지통·숨김 상태로 섞여 있음, **When** 피드를 열면, **Then** 발행된 전체 공개 글만
   처음 공개된 시각 최신순(같으면 번호 큰 순)으로 홈과 같은 카드(작성자 영역 포함) 9개가 보인다.
3. **Given** 9개보다 많은 글, **When** [더 보기]를 누르면, **Then** 다음 9개가 이어지고, 도중에 글이 추가·비공개되어도 중복·누락이
   없으며, 더 없으면 버튼이 사라진다.
4. **Given** 피드를 보던 중 B를 언팔로우함, **When** 다음 요청(새로 열기·[더 보기])을 하면, **Then** B의 글이 빠진다. 이미 화면에
   있는 카드는 그대로다.
5. **Given** 팔로우한 사람이 탈퇴 신청함, **When** 피드를 열면, **Then** 그 사람의 글이 나오지 않는다.
6. **Given** 팔로우한 사람이 없음, **When** 피드를 열면, **Then** "팔로우한 사람이 없어요. 홈에서 읽고 싶은 블로그를 찾아보세요
   [홈]"이 보인다. 팔로우한 사람은 있지만 공개 글이 없으면 "팔로우한 사람의 공개 글이 아직 없어요"가 보인다.
7. **Given** 피드에서 글 상세로 갔다가 뒤로 옴, **When** 피드로 돌아오면, **Then** 이어 붙인 카드와 스크롤 위치가 복원된다.

### User Story 3 - 팔로워·팔로잉 목록으로 새 블로그를 발견한다 (Priority: P3)

누구나 블로그 상단의 "팔로워 N · 팔로잉 N"을 눌러 `/@handle/followers`, `/@handle/following`에서 목록을 보고, 그 자리에서
팔로우할 수 있다.

**Why this priority**: 발견 경로를 넓히지만 팔로우와 피드가 먼저다.

**Independent Test**: 비회원으로 `/@A/followers`를 열어 최근에 팔로우한 순 20개가 보이는지, 탈퇴 신청한 팔로워가 수와 목록에서
빠졌다가 복구하면 돌아오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 누구나(비회원 포함), **When** 블로그 상단을 보면, **Then** "공개 글 N · 팔로워 N · 팔로잉 N"이 보이고 숫자를 누르면 목록으로
   간다.
2. **Given** 목록, **When** 열면, **Then** 각 항목에 프로필 사진, `닉네임 @블로그주소`, 소개 첫 줄, 보는 사람 기준 팔로우 버튼이
   있고, 최근에 팔로우한 순(같으면 회원 번호 큰 순)으로 20개씩 [더 보기]로 이어진다.
3. **Given** 탈퇴 신청한 회원, **When** 남의 목록과 수를 보면, **Then** 그 회원은 빠져 있고, 복구하면 다시 나타난다.
4. **Given** 없는 블로그·탈퇴 신청한 블로그의 목록 주소, **When** 열면, **Then** "찾을 수 없음"이다.
5. **Given** 팔로워·팔로잉이 없음, **When** 목록을 열면, **Then** "아직 팔로워가 없어요" / "아직 팔로우한 사람이 없어요"가 보인다.

---

### Edge Cases

- 팔로우 → 언팔로우 → 팔로우를 반복하면? → 팔로우 자체는 제한이 없고, 같은 사람의 새 팔로워 알림이 7일에 한 번만 가도록
  알림 쪽에서 막는다(알림 기능이 있을 때).
- 언팔로우하면 상대에게 알리나? → 알리지 않는다.
- 피드 커서를 고치거나 다른 목록의 커서를 보내면? → 잘못된 요청으로 거부한다.
- 팔로우 상태를 색으로만 구분하나? → 아니다. 글자와 ✓로 구분한다.
- 관리자는? → 팔로우·피드에서 일반 회원과 같다.
- 팔로우한 사람의 친구 공개 글은? → 친구 공개를 적용하더라도 피드에는 넣지 않는다(공개 글만).
- 탈퇴 신청 회원이 복구하면? → 관계를 지우지 않았으므로 수·목록·피드에 그대로 돌아온다.
- 탈퇴 30일 뒤에는? → 그 회원의 팔로우 관계가 양방향 모두 지워진다.

## Requirements *(mandatory)*

### Functional Requirements

**팔로우 (F-1, F-2, F-5)**

- **FR-001**: 팔로우 대상은 회원(= 블로그)이어야 하며, 관계는 한쪽 방향이고 상대의 승인 없이 바로 맺어져야 한다. 친구 관계와는
  별개 개념으로 함께 있을 수 있어야 한다.
- **FR-002**: 로그인만 하면 팔로우할 수 있어야 한다. 이메일 인증, 인원, 횟수 제한을 두지 않는다.
- **FR-003**: 자기 자신은 팔로우할 수 없어야 하며, 화면에서 버튼을 숨기고 서버에서도 규칙 위반으로 거부해야 한다(데이터 규칙으로도
  막는다).
- **FR-004**: 팔로우·언팔로우는 여러 번 보내도 결과가 같아야 한다. 이미 팔로우 중이면 팔로우가, 팔로우하지 않았으면 언팔로우가 아무것도
  바꾸지 않아야 하며, 응답에는 현재 팔로우 여부와 팔로워 수를 담아야 한다.
- **FR-005**: 동시에 같은 팔로우를 보내도 관계는 하나만 생겨야 한다.
- **FR-006**: 없는 블로그와 탈퇴 신청한 블로그를 대상으로 한 팔로우·목록 요청은 "찾을 수 없음"이어야 한다.
- **FR-007**: 비회원의 팔로우·피드 요청은 로그인이 필요하다는 응답이어야 하고, 화면에서는 로그인 화면으로 보낸 뒤 원래 페이지로
  돌아와야 한다.
- **FR-008**: 팔로우 버튼은 블로그 상단과 글 상세 작성자 영역에 두고, 상태(비회원 [팔로우] / 팔로우 안 함 [팔로우] / 팔로우 중
  [팔로잉 ✓], 올리거나 초점 시 [언팔로우] / 내 블로그·내 글은 버튼 없음)를 글자와 기호로 구분해야 한다.
- **FR-009**: 버튼은 누르는 즉시 바뀌고, 실패하면 원래대로 돌린 뒤 "잠시 후 다시 시도해 주세요"를 보여야 한다. 언팔로우에는 확인 창이
  없어야 한다.

**공개·수 세기 (F-3, F-6)**

- **FR-010**: 팔로워·팔로잉 수와 목록은 비회원을 포함한 누구나 볼 수 있어야 한다.
- **FR-011**: 수는 저장된 숫자가 아니라 그때그때 세어야 하고, 탈퇴 신청한 회원은 빼고 세어야 한다.
- **FR-012**: 목록(`/@handle/followers`, `/@handle/following`)은 프로필 사진, `닉네임 @블로그주소`, 소개 첫 줄, 보는 사람 기준 팔로우
  버튼을 보이고, 최근에 팔로우한 순(같으면 회원 번호 큰 순)으로 20개씩 커서 방식 [더 보기]로 이어야 한다.
- **FR-013**: 목록에서 탈퇴 신청한 회원은 빠져야 하고, 빈 상태에는 "아직 팔로워가 없어요" / "아직 팔로우한 사람이 없어요"를 보여야 한다.
- **FR-014**: 목록은 한 번의 조회와, 보는 사람의 팔로우 여부를 한꺼번에 확인하는 한 번의 조회로 만들어야 한다.

**팔로잉 피드 (F-4, F-7)**

- **FR-015**: 피드는 홈과 별도 페이지 `/feed`이며 로그인이 필요해야 한다. 상단 메뉴의 [피드]는 로그인한 경우에만 보여야 한다. 홈의
  구성은 바꾸지 않는다.
- **FR-016**: 피드 대상은 내가 팔로우한 사람의 글 중 발행·전체 공개·휴지통 아님·숨김 아님·작성자 탈퇴 신청 아님인 글만이어야 하며,
  공개 목록 공용 조건(docs/06 R-2a)을 그대로 써야 한다.
- **FR-017**: 정렬·개수·넘기기는 홈과 같아야 한다: 처음 공개된 시각 최신순(같으면 번호 큰 순), 9개, 다음이 있는지 미리 판단해 빈
  결과 클릭이 없게, 커서 방식 [더 보기]로 중복·누락이 없어야 한다.
- **FR-018**: 카드는 홈과 같은 카드(작성자 영역 포함)여야 한다.
- **FR-019**: 언팔로우하면 다음 피드 요청부터 그 사람의 글이 빠져야 하고, 이미 화면에 있는 카드는 그대로 두어야 한다.
- **FR-020**: 빈 상태는 팔로우한 사람이 없을 때 "팔로우한 사람이 없어요. 홈에서 읽고 싶은 블로그를 찾아보세요 [홈]", 있지만 글이 없을
  때 "팔로우한 사람의 공개 글이 아직 없어요"를 보여야 한다.
- **FR-021**: 상세에서 뒤로 오면 홈과 같이 카드와 스크롤 위치를 복원해야 한다.
- **FR-022**: 피드는 한 번의 조회로 만들어야 한다.

**사건 연동 (docs/20 §3-4)**

- **FR-023**: 팔로우 관계가 실제로 생겼을 때만 "팔로우함"(팔로우한 사람, 받은 사람, 일자) 사건을, 실제로 지워졌을 때만
  "언팔로우함" 사건을 한 번씩 저장이 확정된 뒤 알려야 한다. 사건에는 번호와 일자만 담는다.
- **FR-024**: 사건을 받는 쪽(알림 등)이 실패해도 팔로우·언팔로우는 성공해야 한다.

**권한 (docs/42 §10-1)**

- **FR-025**: 권한은 다음과 같아야 한다: 수·목록 보기는 모두 가능, 팔로우·언팔로우와 피드는 비회원 불가·인증 전 회원 가능·회원 가능·
  관리자는 회원과 같음, 본인 팔로우는 규칙 위반, 없는 블로그·탈퇴 유예 블로그 대상은 모두 "찾을 수 없음".
- **FR-026**: 권한은 화면에서 숨기는 것과 별도로 서버에서 매번 다시 확인해야 한다.

**회원 탈퇴 (docs/24 §6)**

- **FR-027**: 탈퇴 신청(유예) 중에는 관계를 지우지 않고, 그 회원을 남의 수·목록에서 빼고 그 회원의 글을 피드에서 빼야 한다. 복구하면
  그대로 돌아와야 한다.
- **FR-028**: 탈퇴 30일 뒤 정리 단계에서 그 회원의 팔로우 관계를 양방향 모두 지워야 한다(친구 관계 정리 다음 순서, docs/44 §4).

### Key Entities *(include if feature involves data)*

- **팔로우(Follow)**: 팔로우한 회원 → 팔로우받은 회원, 팔로우한 일자. 같은 쌍은 하나뿐이고 자기 자신은 불가.
- **회원(Member)**: 001에서 정의. 상태(탈퇴 신청 여부)로 수·목록·피드 제외를 판단한다.
- **글(Post)**: 002에서 정의. 피드는 홈과 같은 카드 정보를 쓴다.
- **목록 커서(Cursor)**: 003에서 정의. 피드와 팔로워·팔로잉 목록에 각각 쓴다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 대상에 팔로우 요청 20건을 동시에 보내도 관계는 1개, "팔로우함" 사건은 1건이다.
- **SC-002**: 자기 자신 팔로우가 성공하는 경우가 0건이다(화면·서버·데이터 규칙 모두).
- **SC-003**: 피드에 팔로우한 사람의 비공개·임시·휴지통·숨김 글이나 탈퇴 신청 작성자의 글이 섞이는 경우가 0건이다(docs/06 §8 권한
  매트릭스에 "피드" 열 추가).
- **SC-004**: 1,000개 글을 피드 [더 보기]로 끝까지 넘기는 동안 글을 추가·비공개해도 중복·누락이 0건이다.
- **SC-005**: 언팔로우 직후 다음 피드 요청에 그 사람의 글이 나오는 경우가 0건이다.
- **SC-006**: 비회원이 팔로워·팔로잉 수와 목록을 볼 수 있고, 탈퇴 신청한 회원은 빠졌다가 복구하면 100% 돌아온다.
- **SC-007**: 탈퇴 30일 뒤 처리 후 그 회원이 들어간 팔로우 관계가 양방향 모두 0개다.
- **SC-008**: 팔로워 1만 명인 블로그에서도 블로그 상단의 팔로워 수가 일반적인 회선에서 1초 안에 보인다.
- **SC-009**: docs/24 §9의 공통 완료 기준 7개가 모두 자동 테스트로 확인된다.

## Assumptions

- **A-1**: 새 팔로워 알림(같은 사람 7일 1번, 안 읽은 동안 묶기)과 팔로우한 사람의 새 글 알림(처음 전체 공개될 때 한 번)은 알림 기능
  (docs/25)이 들어올 때 이 기능의 사건을 받아 처리한다. 이 spec은 사건을 알리는 데까지 책임진다.
- **A-2**: 2026-10-07 화면 방식 결정(React + 서버 API)에 따라 docs/24의 "JS 없을 때 `/feed?cursor=…` 링크로 동작"하는 대체 규칙과
  폼 전송 팔로우는 범위 밖이다.
- **A-3**: MVP 로그인은 GitHub 단독이어서 이메일 인증 전 회원이 사실상 없지만, 팔로우는 인증과 무관하게 허용하는 규칙을 그대로 둔다.
- **A-4**: 팔로워가 1만 명을 넘는 회원이 생기면 팔로워 수를 저장해 두는 방식(매일 보정)을 검토하고, 팔로우한 사람이 수천 명인 사용자가
  생기면 피드를 미리 만들어 두는 방식을 검토한다. 둘 다 지금 범위가 아니며, 도입하면 F-6 변경이라 팀에 알린다.
- **A-5**: 블로그 구독(나민서)·그룹(강성찬)은 개인 확장이다. 블로그 구독은 화면 이름만 다르게 하고 이 팔로우 관계를 쓴다.
- **A-6**: 팔로우에 별도 요청 횟수 제한이 없으므로 공통 IP 요청 제한 기준에 포함되는지는 팀 확인 사항이다(미결).
- **A-7**: 관리자 숨김(019)이 아직 없을 때도 피드 대상 조건은 처음부터 공용 조건(숨김 제외 포함)대로 둔다.
