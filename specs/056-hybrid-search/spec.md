# Feature Specification: 하이브리드 검색 (키워드 + 의미)

**Feature Branch**: `claude/project-thread-78wl06`
**Created**: 2026-10-08
**Status**: Implemented (v1.32.0)
**근거**: 블로그 주인 요청 "하이브리드 검색으로 해야될 거 같은데… 검색이 안되면 UX가 많이 낮아질 거 같아", "필요하면 배치도 사용해서 임베딩 해줘". 014 검색은 `ILIKE` 부분 일치라 "롤백 처리"로 검색하면 "트랜잭션" 글을 0건으로 돌려줬다.

## 정한 것과 이유

| 갈림길 | 고른 것 | 이유 |
| --- | --- | --- |
| 검색 엔진 | PostgreSQL 하나(pg_trgm + pgvector) | 운영 DB가 1.25.1부터 pgvector 이미지다. Elasticsearch는 서버·동기화가 하나 더 늘어 지금 규모에선 부담이 크다. 글이 수십만 개가 되거나 한국어 형태소 분석이 필요해지면 다시 본다 |
| 섞는 방법 | RRF(순위 섞기), 의미 쪽 무게 0.8 | 키워드 순위와 거리 점수는 단위가 달라 점수를 더하기 어렵다. 순위만 쓰면 안정적이고, 무게를 1보다 낮춰 제목·태그에 그대로 있는 글이 위에 남는다 |
| 임베딩 모델 | Ollama `bge-m3`를 **서버 안**에 CPU로 | 검색어도 검색할 때마다 같은 모델로 임베딩해야 한다. 집 PC에만 두면 PC가 꺼졌을 때 의미 검색이 멈춘다. 다국어(한국어) 성능이 좋고 무료다 |
| 공급자 순서 | 서버 안 Ollama → 집 PC Ollama → Gemini | 같은 `bge-m3`면 서버 안·집 PC 벡터를 섞어도 된다. Gemini는 다른 모델이라 저장 벡터에 모델 이름을 적어 섞이지 않게 한다 |
| 글 임베딩 시점 | 1분마다 "임베딩이 없거나 그 뒤로 고쳐진 공개 글"을 20개씩 **한 요청으로 묶어** | 대기열 없이도 발행·수정·기존 글·밀린 글이 같은 길로 채워지고, 두 번 처리해도 덮어쓰기라 결과가 같다 |
| 실패할 때 | 그 검색은 키워드만, 60초 동안 공급자를 건너뜀 | 의미 검색은 덤이다. 검색이 느려지거나 실패하면 안 된다 |
| 최신순 | 키워드만 | 최신순은 "검색어가 들어 있는 글을 날짜순"이라는 뜻이 분명하다 |

## 사용자 시나리오

1. **Given** "스프링 트랜잭션 정리" 글, **When** "롤백 처리"로 검색하면, **Then** 검색어가 글에 없어도 그 글이 나오고 카드에 "비슷한 글" 표시(툴팁: 검색어가 그대로 들어 있지 않지만 내용이 비슷해 찾은 글이에요)가 붙는다.
2. **Given** 제목에 "롤백"이 있는 글과 트랜잭션 글, **When** "롤백"으로 검색하면, **Then** 제목에 있는 글이 먼저, 뜻이 가까운 글은 뒤에 나온다. 도커 글처럼 관계없는 글은 나오지 않는다.
3. **Given** 임베딩 모델이 꺼져 있음, **When** 검색하면, **Then** 지금까지와 같은 키워드 결과가 나오고 60초 동안은 모델을 부르지 않는다.
4. **Given** DB에 pgvector가 없음(학교 공용 DB), **When** 앱이 뜨면, **Then** 마이그레이션은 표 없이 지나가고 검색은 키워드만 쓴다.
5. **Given** 공개 글 여러 개, **When** 임베딩 작업이 돌면, **Then** 한 요청에 여러 글을 묶어 보내고, 비공개·친구 공개 글은 보내지 않는다. 고친 글은 다음 차례에 다시 임베딩한다.
6. **Given** 키워드 결과가 많음, **When** [더 보기]로 넘기면, **Then** 섞은 목록 뒤로 남은 키워드 결과가 빠지거나 겹치지 않고 이어진다.

## Requirements

- **FR-001**: `post_embedding(post_id, model, source_version, embedding vector)`(V16). `vector` 확장을 만들 수 없으면 표를 만들지 않는다(V2와 같은 방식). 차원은 모델마다 달라 열에 고정하지 않고 같은 `model` 행끼리만 비교한다.
- **FR-002**: 관련도순이고 의미 검색을 쓸 수 있으면, 키워드 결과 앞쪽 100개와 의미 검색 30개(코사인 거리 0.55 이하, Gemini는 0.4)를 RRF(k=60, 의미 무게 0.8)로 합친다. 점수가 같으면 키워드 순위가 앞선 글이 먼저다.
- **FR-003**: 섞은 목록은 커서 `{9, 위치, 0}`로 넘긴다. 목록이 끝나고 그 뒤로 키워드 결과가 더 있으면 일반 키워드 커서로 이어지고, 섞은 목록에서 이미 보여 준 의미 검색 글은 빼고 낸다.
- **FR-004**: 결과 카드에 `similar`(검색어가 그대로 없고 뜻으로만 찾은 글)를 더한다. 화면은 "비슷한 글" 표시와 툴팁을 단다. 그 글의 미리보기는 강조 없이 본문 앞부분이다.
- **FR-005**: 검색어 벡터는 Redis에 하루 보관한다(열쇠는 검색어 해시, 원문은 남기지 않음). 공급자 연결에 실패하면 `search:embed:down`을 60초 둔다. 검색어 임베딩 시간 제한은 3초다.
- **FR-006**: 임베딩 작업은 1분마다 한 서버만(JobLock) 돈다. 공개 글만, 최신 글부터 20개씩 최대 10묶음. 넣는 글자는 제목 + 태그 + 본문 글자 앞 3000자다.
- **FR-007**: 배포(selfhosted)는 클러스터 안에 `ollama-embed`(ollama/ollama, bge-m3, CPU, 앱 파드에서만 접속)를 띄우고 `EMBED_BASE_URL`로 가리킨다. 모델은 처음 뜰 때 받아 볼륨에 둔다.
- **FR-008**: 설정 `blog.search.semantic.*`(`SEARCH_SEMANTIC_ENABLED`, `SEARCH_EMBED_PROVIDER`, `EMBED_BASE_URL`, `EMBED_MODEL`)으로 끄거나 공급자를 고를 수 있다.

## 범위 밖
- HNSW 인덱스(글이 수만 개를 넘으면 모델을 하나로 정하고 차원을 고정한 뒤 더한다).
- 사람 검색의 의미 검색, 최신순 하이브리드.
- 거리 기준값을 실제 글로 맞추기(운영 글이 쌓이면 다시 본다).
